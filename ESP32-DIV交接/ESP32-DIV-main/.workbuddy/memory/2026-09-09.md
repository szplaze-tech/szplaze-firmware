# 2026-09-09 工作日志

## SubGHz Jammer 频率打偏（目标频率无影响、邻频才有干扰）

**现象**：SubGHz Jammer 设好频率开 Toggle 后，目标频率上接收机没反应，把接收机调到**相邻频率**反而收到干扰。

**硬件前提（用户实测确认）**：CC1101 晶振 **26MHz**（不是 27MHz，排除晶体频偏假设）；Replay Attack 能抓到对讲机信号 → 频率合成/RX 是准的。

### 根因：四个 bug 叠加，核心是「异步透明模式下调制源是 GDO0 引脚」

1. **库默认工作在异步透明串行模式**：`setCCMode(false)` → `PKTCTRL0 = 0x32`（PKT_FORMAT=3 异步 + LENGTH_CONFIG=2 无限包长）。此模式下**发送符号采样自 GDO0 引脚，TX FIFO 完全不参与调制** —— 原代码往 `CC1101_TXFIFO` 写 0xFF/随机噪声**对射频输出无效**。
2. **推错了引脚**：`digitalWrite(TX_PIN, HIGH)` 推的是 **TX_PIN=GPIO3**，而 V2 下 GPIO3 = `SUBGHZ_RX_PIN` = **GDO2（接收脚）**；真正的数据脚 `CC1101_GDO0 = SUBGHZ_TX_PIN = GPIO6` 从未被设置 → 浮空。（这正是社区 #35 说的 GDO0/GDO2 命名反了）
3. **调制方式错**：`setModulation(0)` = 2-FSK。GDO0 浮空被采成常量"0" → 持续发 fc − deviation ≈ **fc − 47.6 kHz** 的单频 → 干扰落在邻频。
4. **每帧重启 TX**：`subjammerLoop()` 里每个 loop 都 `SetTx()`（SIDLE+STX），把载波打碎成宽带突发脉冲串，能量进一步扩散。

另外 `subjammerSetup()` 结尾直接 `SetTx()` → **一进 Jammer 界面就在发射**（jammingRunning 还是 false，UI 显示 stopped）；退出 jammer 时也没停载波。

### 修复（subghz.cpp，subjammer 命名空间）

- 新增 `subjammerStartCarrier()` / `subjammerStopCarrier()`：
  - `setModulation(2)` 切 **ASK/OOK**（GDO0 高电平 = 未调制载波，精确落在 fc）；
  - 驱动 **CC1101_GDO0（GPIO6）** 而非 TX_PIN；
  - `continuousMode=true` → GDO0 常高（纯载波点频）；`=false` → LEDC CH5 输出 100kHz 方波展宽成噪声；
  - 停止时 `ledcDetachPin` + GDO0 拉低 + `pinMode(INPUT)` 交还 CC1101 + `setSidle()`。
- `subjammerToggleJam()` / `subjammerApplyFrequency()` 改用新函数；删除 loop 里逐帧 `SetTx()+写FIFO` 那 17 行。
- 触摸图标 case 0 复用 `subjammerToggleJam()`（原来有重复逻辑）；case 1 切模式后若正在发射则重建载波。
- setup 改 OOK + `setSidle()` + GDO0 输出低（进界面不再发射）；`subjammerLoop()` 退出分支加 `subjammerStopCarrier()`。

**编译 EXIT=0，零代码警告，Sketch 1738557B(88%)。**

### 关键知识点（可复用）
- ELECHOUSE CC1101 库 `SetTx()` 只是 `SIDLE`+`STX`，**不写 FIFO**；异步模式下必须驱动 GDO0。
- V2 引脚映射：`SUBGHZ_RX_PIN=GPIO3=GDO2`、`SUBGHZ_TX_PIN=GPIO6=GDO0`；老宏 `TX_PIN=3`/`RX_PIN=6` 与之**相反**，是坑。
- 2-FSK 常量符号会让载波停在 fc±deviation（库默认 DEVIATN=0x47 → 47.6kHz），做点频干扰必须换 OOK。
- LEDC 通道占用：`PWM_CHANNEL=0`（背光）、`BUZZER_LEDC_CH`（subghz.cpp），jammer 新增用 **CH5**。

## 第一次修复失败：改完反而完全无输出（用户反馈"连之前都不如"）

**原因（我的误判）**：我默认库初始化后就是异步模式，实测库源码推翻：
- `RegConfigSettings()` **从不写 PKTCTRL0** → `Init()` 后芯片停留在复位默认 **FIFO 模式 `PKTCTRL0=0x45`**；
- 只有 `setCCMode(0)` 才切成异步 `PKTCTRL0=0x32`；工程里 setCCMode 只在 1427(Replay)/2301/3120/3721 调用，**Jammer 从不调用**。
→ 芯片实际在 FIFO 模式；原代码每帧写 FIFO 才有输出，我删掉写 FIFO 后 FIFO 空 → TX underflow → 完全无射频输出。

**重要副作用（状态依赖，工程通病根源）**：CC1101 的包格式不随功能重置，取决于之前进过哪个功能——先进 Replay（设了异步）再进 Jammer 就是异步，直进 Jammer 就是 FIFO。这是该工程大量"时好时坏/换个顺序就好了"现象的共同根源。

## 第二次修复（正确版）

- `subjammerStartCarrier()` 显式 `setCCMode(0)` 强制异步透明模式（顺序：setSidle → setCCMode(0) → setModulation(2) → setMHZ → setPA → GDO0 → SetTx）。
- 新增 `subghzMarcState()`：`SpiReadBurstReg(CC1101_MARCSTATE | 0xC0, ...)` 读状态寄存器（`SpiReadBurstReg` 内部会 OR `READ_BURST`）。MARCSTATE：0x01=IDLE / 0x0D=RX / **0x13=TX** / 0x16=TXFIFO_UNDERFLOW。
- 开载波后串口打印 `[JAM] carrier on marc=0xXX (TX=0x13)`；loop 加 500ms 看门狗，marc≠0x13 则重建载波并打印 `[JAM] watchdog: ...`。
- 编译 EXIT=0，Sketch 1738789B(88%)。

## 实测反馈（第二次修复后）

用户烧录后串口：`[JAM] carrier on marc=0x08 (TX=0x13)`。

**0x08 = STARTCAL（频率合成器校准中），不是错误**——诊断打印位置有缺陷：`SetTx()` 只是发 STX 命令，从 IDLE 到真正建立载波需约 0.7~1ms，零延时读 MARCSTATE 必然读到中间态。
→ 改进点：`SetTx()` 后应 `delay(2~5)` 再读 MARCSTATE 才是稳态值。

**真正的判据是看门狗**：loop 每 500ms 只在 marc≠0x13 时打印 `[JAM] watchdog: ...`。
- `carrier on` 之后**无** watchdog 行 → 芯片稳定停在 TX(0x13) → 正在发射 ✓
- 持续出现 watchdog 行 → 芯片被反复踢出 TX，需查硬件/GDO0

MARCSTATE 速查：0x01=IDLE / 0x08=STARTCAL / 0x09=BWBOOST / 0x0D=RX / **0x13=TX** / 0x16=TXFIFO_UNDERFLOW。

## 重要实测反转（16:07）：原版 Jammer 其实能在目标频率收到

用户把对讲机 **SQL 设到 1 以下**（此前是打开了降噪导致听不到），回滚版 SubGHz Jammer 设好频率开 Toggle 后，**对讲机在设定频率收到"有规律间隔的嘟嘟声"**。

**结论：发射链路和频率都是准的，我此前"频率偏 47.6kHz / 只在邻频有干扰"的判断是错的**（那次是降噪设置 + 验证方法导致的误判）。

**嘟嘟声成因（完全对得上代码）**：
1. 原版 loop 每帧都 `SetTx()`（内部 `SIDLE`+`STX`）→ 载波被周期性重启 → 听到的就是**间隔的"嘟"**；
2. FIFO 模式下写入的第 1 个字节被当作**长度字节**（写 0xFF = 长度 255，却没有数据）→ TX 下溢 → 实际发出去的是 **preamble**（2-FSK 交替 1010）；
3. 2-FSK preamble 频谱是**双峰**(fc±deviation)，但**中心仍在 fc** → 所以设定频率上收得到 ✓。

→ 即：频率准，但输出是"被斩断的脉冲 + 双峰谱"，干扰效率低（能量被摊到两峰且不连续）。

**后续若优化，最小改动**：去掉 loop 里每帧 `SetTx()`，并在 setup 设 `MCSM1 = 0x30`（TXOFF_MODE=0，发完保持 TX 不退出），即可从"嘟嘟"变"持续压制"。若要能量集中到单一频点，再切 OOK + 持续填 FIFO（异步 GDO0 那条路实测未成功，优先走 FIFO）。

## Replay Attack：Send 卡很久 + 界面显示 65535/4294967295（16:42）

**现象**：进 Replay Attack 界面显示 `Freq 418.000 / Ptc 65535 / Bit 65535 / Rssi -100 / Val 4294967295`；点 Send 后长时间停在 Sending（对讲机确实收到发射），久到不正常。

**根因（同一个）**：`ReplayAttackSetup` 从 EEPROM 恢复上次捕获的码（`ADDR_VALUE/BITLEN/PROTO`，1355-1357），**未做有效性校验**。EEPROM 全新/擦除时读出全 `0xFF` → `receivedValue=0xFFFFFFFF(4294967295)`、`receivedBitLength=0xFFFF(65535)`、`receivedProtocol=0xFFFF(65535)`。
而 `sendSignal()`（1009）**无任何校验**直接 `mySwitch.send(receivedValue, receivedBitLength)` → **发送 65535 位**，RCSwitch 是阻塞式（delayMicroseconds 逐位），×`setRepeatTransmit(8)` → 卡住数分钟。界面显示的那三个值也正是 EEPROM 的 0xFF 填充。

**修复（两处，编译 EXIT=0，Sketch 1738561B）**：
1. EEPROM 读取后加校验（1358 附近）：`value==0xFFFFFFFF || value==0 || bitLength==0 || bitLength>64 || protocol==0xFFFF` → 全部清零，视作"尚未捕获"。
2. `sendSignal()` 开头加守卫：无效值直接显示红色 `No signal captured!` 并 return，不进入发射流程。

**经验**：`0xFFFFFFFF / 65535` 这类"全 1"数出现在 UI 上，先怀疑 **EEPROM/Flash 未初始化读出 0xFF**，而不是传感器/解码器坏了。

## Replay 抓不到对讲机信号：调制方式不匹配（非 bug）

用户反馈：EEPROM 修复生效（界面 0/0/0），RSSI 波形有反应，但对讲机 PTT 后 Val/Bit/Ptc 不刷新。

**结论**：Replay Attack 配置为 **ASK/OOK**（1454-1455：`setCCMode(0)` + `setModulation(2)`，RCSwitch 也只解 OOK）；**宝峰对讲机是 FM 调制**——OOK 解调器物理上解不出 FM 信号，只有 RSSI 能量反应，永远不会有解码输出。波形动而 Val=0 = 预期行为。

**正确测试信号源**：
1. ASK/OOK 遥控器：433.92MHz 无线门铃/车库门/窗帘/车钥匙（频率列表里有 433.920）；
2. 用另一块 ESP32-DIV（用户有两块 S3 板）做发射源：一块用 Brute/Saved Profile 发 OOK 码，另一块 Replay 收。

**经验**：Replay/SubGHz 的接收解调是 OOK，**FM 音频信号只能让波形动、抓不出码**——验证接收时必须用 OOK 信号源。
