## 2.4G Scanner 实现要点（测试参考）

- 位置：`namespace Scanner`（bluetooth.cpp:4032+），检测原理 = nRF24 **RPD 寄存器 0x09**（Received Power Detector，>-64dBm 置位），逐信道采样画柱状图；
- 用的 nRF24 #3（CE=GPIO14 / CSN=GPIO21，`NRF24_SCAN_CE/CSN`）→ 与 IR 引脚冲突，测 Scanner 前别碰 IR 功能；
- 频率换算：nRF channel N = 2400+N MHz。WiFi ch1=2412=第12信道、ch6=2437=第37、ch11=2462=第62（WiFi 20MHz 带宽≈25 个 nRF 信道）；BLE 广播=2402/2426/2480=第2/26/80 三根尖峰。

### 三颗 nRF24L01 的引脚与功能归属（V2）

| 模块 | CE | CSN | 用途 |
|---|---|---|---|
| **#1** | GPIO15 | GPIO4 | BleJammer / ProtoKill（channelGroup1） |
| **#2** | GPIO47 | GPIO48 | BleJammer / ProtoKill（channelGroup2） |
| **#3** | GPIO14 | GPIO21 | **Scanner / ESB Sniffer / ESB Replay / MouseJack 全部 5 个功能**（`NRF24_SCAN_CE/CSN`）；BleJammer/ProtoKill 也用它（channelGroup3） |

- 三颗**共享 SPI 总线**（V2：SCK=12/MISO=13/MOSI=11），靠各自 CSN 片选；`NRF24_SPI_SS=4` 与 `CSN_PIN_1` 同脚；
- **BleJammer（bluetooth.cpp:3122）和 ProtoKill（4997）是三颗并发**（分 channelGroup1/2/3 覆盖更多信道），这才是板上焊 3 颗的意义；

### 关键对照实验（17:39）：外部模块 OK，板载 nRF24 不行

用户用 ESP 开发板 + 杜邦线外接 nRF24L01 模块，Scanner **能正常显示柱状图** → 证明**软件逻辑 + 模块型号 + 代码配置全部没问题**，问题锁定在 **ESP32-DIV 板载 nRF24 的硬件链路**。

**已排除的怀疑**：GPIO11 可用性——Arduino ESP32-S3 变体默认 SPI 就是 `MOSI=11/MISO=13/SCK=12/SS=10`（variants/esp32s3/pins_arduino.h:33-36），与代码 `NRF24_SPI_*` 完全一致，GPIO11 在 Arduino 环境下是合法 SPI MOSI。

**剩余怀疑（待用户排查）**：
1. **IR 功能污染**（高）：GPIO14(CE#3)/GPIO21(CSN#3) 与 IR TX/RX 共用，进过 IR 后 GPIO14 可能停在 OUTPUT 低、GPIO21 停在 INPUT_PULLUP → CE 低/CSN 失效 → #3 不响应。**测 Scanner 前先重启一次整机**（社区 #102"切功能间重启"）。
2. **pogopin 接触**（社区通病）：下层板经 pogopin/排针对接上层板，冷焊/氧化导致 nRF24 掉线。
3. **板载 3.3V 供电**未到 nRF24 模块。
4. **天线插错口**——Scanner 用 #3，插到 #1/#2 的 SMA 口则全程无反应。

**外部开发板已确认是 ESP32-S3（18:17）** → 同一代码、同一 S3 引脚定义（11/12/13 + CE14/CSN21）下，杜邦线外接模块 Scanner 出图正常，而板载 nRF24 无反应。
**结论：软件、引脚定义、GPIO11 可用性、模块型号全部排除；问题 100% 在"上层板 GPIO → 下层板 nRF24"的物理链路**（走线 / pogopin / 供电 / 模块焊接 / 天线口）。

**下一步排查顺序（一次一个变量）**：
1. 整机重启后进 Scanner（排除 IR 污染：GPIO14 停在输出低 / GPIO21 停在输入上拉）；
2. 下层板 nRF24 #3 的 VCC-GND 是否 3.3V；
3. 压紧两层板（pogopin 接触）再进 Scanner；
4. Scanner 运行时量 SCK(GPIO12) 有无时钟活动、CSN(GPIO21) 有无周期拉低 —— 判断信号是否到达下层板；
5. 若信号到了但无响应 → 查 #3 模块焊接/是否贴片、天线是否插在 #3 对应 SMA 口。

**教训**：该板是复刻板，**原理图与实际存在出入**（此前 IP5306 分压比实测 6.6:1 与图上判读的 2:1 不符），不能盲信原理图，一切以实测为准。

- 库：**RF24 1.6.2**（TMRh20 标准库），目标型号 nRF24L01+ / nRF24L01 通用；
- **代码实际只用 2Mbps**：`setDataRate(RF24_2MBPS)` 两处（bluetooth.cpp:3230、5123）；**全工程搜不到 250KBPS** → 老版 nRF24L01（不带 +，仅支持 1M/2M）**完全兼容可用**；
- `NRF24_DATA_RATE=2` / `NRF24_PA_LEVEL=3` 两个宏在 .cpp/.ino 里**从未被引用**（死配置）——若哪天真按 250kbps 用起来，老版模块才会失效；
- 2Mbps 下老版与 + 版灵敏度相同（-82dBm），Scanner(RPD 能量检测)/ESB/MouseJack 都不受影响。
- 其余 5 个 2.4G 功能**只用 #3** → 测试 Scanner 时天线必须插在 **#3 对应的 SMA 口**，插错口会完全没反应（这是"Scanner 无反应"的首查项）。
- 若不知哪个口是 #3：开 Scanner + 手机开 WiFi 热点贴近，天线逐口轮换，柱状图有反应者即 #3 所在口（或查 PCB 丝印/原理图网络）。

## 红外(IR) 与 nRF24L01 #3 引脚冲突（V2 实锤，shared.h 560-662）

**V2 分支引脚完全重叠：**
- `IR_TX_PIN = 14` == `CE_PIN_3 = 14`（nRF24 #3 的 CE）
- `IR_RX_PIN = 21` == `CSN_PIN_3 = 21`（nRF24 #3 的 CSN）

**使用方**：2.4G 菜单的 Scanner / ESB Sniffer / MouseJack 全用 nRF24 #3（bluetooth.cpp：`RF24 radio3(CE_PIN_3, CSN_PIN_3)` ×2 处 + `#define CE NRF24_SCAN_CE` ×5 处）。**作者在 shared.h 639-640 注释里自己承认了重叠**（"Default pins overlap with the optional NRF24 #3 wiring"）。

**冲突机理**：IR 发射时 GPIO14 输出 38kHz 载波 = 直接灌进 nRF24#3 的 CE 脚（硬件并联，软件无法隔离）；IR 接收时 GPIO21 配成输入上拉 = CSN 电平失控。ir.cpp:1192-1193 进功能时会重新 pinMode（GPIO21 INPUT_PULLUP / GPIO14 OUTPUT），RF24 begin 也会重配 CE/CSN——所以"顺序使用+重新进入"多数能自愈，真正的坑是 ledc 残留（IRsend 38kHz 载波若不 detach，退出后还在打 CE）和发射中途。社区 #102"切功能间最好重启一次"就是这个原因。

**硬件注意**：这是并联在同一对 GPIO 上的设计（官方 V2 即如此，用户自研板同布局），IR 与 nRF24#3 **不可同时使用**，只能靠切换清理。

**待验证**：交叉测试 2.4G Scanner → IR 发射 → 再进 Scanner，观察是否异常；退出 IR 时可加 ledcDetachPin(IR_TX_PIN) 清理保险。另：IRremoteESP8266 的 IRsend 在 ESP32 上默认用 LEDC 通道可能撞背光（PWM_CHANNEL=0），需留意。

### 中断残留才是真凶（10:30 查实并修复）

查库源码（IRremoteESP8266 v2.9.x）修正两点：
1. **IRsend 不用 LEDC**（全库 grep 不到 ledc）——38kHz 载波是**软件 bit-bang** 翻转，发射结束无残留载波，"ledc 撞背光"的担心排除；
2. **IRrecv 用 GPIO CHANGE 中断**（IRrecv.cpp:413 `attachInterrupt(recvpin, gpio_intr, CHANGE)`）——这才是真正的雷。

**致命路径**：IR 三个功能（Record/IRSavedProfile/IRUniversalController）的 loop 退出分支**全都没调 `disableIRIn()`**（只设 feature_exit_requested 就 return）→ GPIO21 的中断永远挂着 → 之后进 Scanner/ESB/MouseJack，GPIO21 变成 nRF24#3 的 CSN，**每次 SPI 片选电平跳变都触发红外 gpio_intr** → SPI 密集操作时中断风暴 → 卡顿/WDT/内存损坏（与社区 #35 的 GPIO16 RCSwitch 同族）。

**修复（编译 EXIT=0，Sketch 1738609B）**：ir.cpp 三个 loop 的退出分支统一加 `IRRemoteFeature::s_recv.disableIRIn();`（用限定名，因 s_recv 是 IRRemoteFeature namespace 内 static；tryReplay 里原有的一处也统一了）。IRRemoteFeature::loop 里用限定名访问自己 namespace 的变量也合法。

**回答用户的问题（IR 会不会影响 2.4G）**：
- 中断残留路径：**会且严重**（已修）；
- 引脚电平路径：轻，功能切换时 RF24 begin 重配 CE/CSN 可自愈；
- IR 发射对 2.4G 的实时干扰：IR 与 nRF24#3 硬件并联同一对脚，IR 发射期间 2.4G#3 必然被扰，**两者不可同时使用**——这是硬件设计限制。
