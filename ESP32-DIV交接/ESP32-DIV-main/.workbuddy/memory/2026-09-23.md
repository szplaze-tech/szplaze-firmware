**A. I2C 模式（零新增引脚）**

### 🐞 实机回执：进 RFID 卡死（点不动、退不出）—— 两层原因

**现象**：选中 RFID 任一功能 → 屏幕停在同一页、触摸与按键都不响应。

**第 1 层（真正的锁死）：`otherDismissPlaceholder()` 的两个 `while` 没有超时**
```cpp
while (isButtonPressed(BTN_SELECT) || isButtonPressed(BTN_LEFT)) { delay(5); }   // ← 无上限
```
`isButtonPressed()` 最终走 `pcf.digitalRead()`，而 **PCF8574 库在 I2C 读失败时不报错**：
`digitalRead()` 里 `value = (bit(pin) & readModePullUp) ? HIGH : LOW`，
读失败时 `byteBuffered` 不更新，会走到 `bit(pin) & byteBuffered` 为 0 的分支 → 返回 **LOW**
→ `isPhysicalButtonPressed()` 的 `!digitalRead()` 变成 **true**。
**⇒ 只要 I2C 总线被拖死，所有按键都被读成"一直按住" → 上面那个 while 永久空转 → UI 锁死。**
（这解释了"退不了"；且该现象**只在 I2C 总线异常时出现**。）

**第 2 层（我引入的放大）：探测太慢，被误当成"点了没反应"**
库的 `waitready(100)` 是**按 10ms 步进空转**到超时的；总线异常时每次 `isready()`
（= 一次 I2C 读）还要再吃一次 `Wire` 超时。我上一版把探测期超时放宽到 **200ms**，
于是最坏 `4 × waitready × (200ms + 10ms) ≈ 3.4~5s` 完全无响应。
**⇒ 放宽超时等于把"总线异常时每次事务阻塞多久"放大 4 倍。**

**修法（三层，已编译 EXIT=0 / 1778457 B / 零告警）**
1. `otherDismissPlaceholder()` 两个循环加上限：释放等待 3000ms、等待点击 8000ms
   ⇒ 无论输入侧发生什么，界面一定能在有限时间内回来。
2. `otherRfidPlaceholderAction()` 加**纯 ACK 闸门**：先 `i2cPing(0x24)`，
   不应答就**不进库里的慢探测**，几百毫秒内给结论。
3. 新增 `i2cPing(addr)`（`beginTransmission` + `endTransmission()==0`，健康总线 ~0.1ms）
   与屏幕自检条 `otherRfidProbeBanner()`（**三行，占顶部 46px**）：
   ```
   RFID: PN532 NOT ready
   <verdict>
   I2C  0x20:OK 0x75:OK 0x24:--
   ```
   **判读**：0x20(键盘)/0x75(IP5306) **一起**变 `--` ⇒ 总线被 PN532 拖死（硬件）；
   只有 0x24 是 `--` ⇒ 只是 PN532 没应答。
   **失败时会重新体检一次**（`pcfAck1/pmicAck1/nfcAck1`）并显示**探测后**的状态 ——
   若探测前全 OK、探测后变 `--`，说明是探测过程本身把总线弄死的，信息量最大。
4. `PN532_I2C_TIMEOUT_MS` 200 → **100**（只放宽 2 倍）。
5. `ESP32-DIV.ino` 补 `#include "ip5306.h"`（原来只有 ip5306.cpp/utils.cpp 有，
   主 ino 看不到 `IP5306_ADDR`）。

**给用户的现场判据**

### 🔎 用户回执（10:30）：屏幕提示「没有找到模块」

即 `RfidNfc::begin()` 返回 false。固件侧已确认无误（构造走 I2C 重载、`Wire` 是
port0 → 默认 GPIO8/9、地址 0x24、库其余环节都有界），所以**问题在硬件侧**。

**"没找到"只有两种分支，靠自检条区分**
- `0x20:OK 0x75:OK 0x24:--` ⇒ 总线健康，只是 PN532 不应答 → 查接线/SEL/RSTPDN
- `0x20:-- 0x75:-- 0x24:--` ⇒ 模块把整条总线拖死 → 先拔模块复测

**嫌疑清单（按可能性排序）**
1. **SEL 开关不在 I2C 档** —— HSU/SPI 档下模块的 UART/SPI 缓冲器会主动驱动 SDA/SCL
2. **接了 MOSI/MISO 而不是 SDA/SCL** —— 模块这两种脚是分开引出的，极易搞混
3. **RSTPDN 悬空** ⇒ 芯片可能一直处于复位态、完全不响应。
   固件目前 `PN532_I2C_RST = -1`（不驱动）。**可把模块 RSTPDN 接到 GPIO1**
   （原 WS2812 焊盘，固件零占用；驱动为高时 WS2812 的 DIN 长期高电平不会点灯）
   并把 `PN532_I2C_RST` 改成 `1`，让库主动做一次 `LOW 1ms → HIGH` 复位。
4. 模块供电（VCC 悬空时 I/O 的 ESD 二极管会箝位总线；供 5V 则总线上拉到 5V）
5. SDA/SCL 接反

**备用信息通道**：`ip5306.cpp` 的 `IP5306_SCAN_DEBUG`（默认 0）改 1 后，
上电会往 Serial 打 `[IP5306] scan: N device(s): 0x.. 0x..`（扫 0x03–0x77）。
但本机 USB 走了 `CDCOnBoot=default`（Serial = UART0 GPIO43/44，非 USB-CDC），
且 CP2102 已刷坏需飞线，所以**屏幕自检条是主通道**。

**处置：固件驱动 RSTPDN（GPIO1 = 原 WS2812 焊盘，固件零占用）**
- `shared.h`：`PN532_I2C_RST` V2 默认从 `-1` 改为 **`1`**。
- `rfid.cpp`：新增 `rfidResetPulse()`（`LOW 5ms → HIGH` + `delay(60)` 等启动）+ 公开 API
  `RfidNfc::hardwareReset()`（`rfid.h` 已声明）。
- `ESP32-DIV.ino`：`otherRfidPlaceholderAction()` 里**先** `hardwareReset()`，
  **再**ping（这样自检条反映的是复位后的真实状态）。
- ⚠ **构造函数仍传 `-1` 给 RST**，不是笔误：库在**全局构造期**就 `pinMode(_reset, OUTPUT)`，
  早于 `initArduino()`，有踩未初始化外设管理器、开机即挂的风险。复位改在 begin 阶段手动做。
- 副作用：GPIO1 驱动为高时 WS2812 的 DIN 长期高电平不点灯；LOW 脉冲只是一个"复位"位型，也不发光。

**如果接上 RSTPDN 后仍是 `0x24:--`，剩下的嫌疑人（按可能性）**
1. **SDA/SCL 接反**（对 PN532 丝印）—— 不影响板上 0x20，所以与现象完全自洽
2. **接了 MOSI/MISO 而不是 SDA/SCL** —— 模块这两种脚分开引出，极易搞混
3. 模块 VCC 悬空（I/O 的 ESD 二极管箝位）或供了 5V

**顺带修的**：自检条 verdict 文案都压到 **≤39 字符** —— font1 是 6px/字，
240 宽只能放 40 字，原 `PN532 absent - check SDA/SCL + SEL switch`(41) 会被裁掉 1 字。

### 🐞 用户回执（10:52）：接线修好后 `0x24:OK`，但"进去卡住"

**用户确认是自己线接错了**；改对后 `0x24` 已应答（说明 RSTPDN 那条也生效了）。
新现象：自检条打出 `0x20:OK 0x75:-- 0x24:OK` 后卡住。

**核查结论：不是死锁，是"长阻塞"**
读 ESP32 core 源码确认 `i2cWrite` / `i2cRead`（`esp32-hal-i2c.c`）的临界区都是有限的：
```c
if (bus[i2c_num].lock == NULL || xSemaphoreTake(bus[i2c_num].lock, portMAX_DELAY) != pdTRUE) ...
...
ret = i2c_master_cmd_begin(i2c_num, cmd, timeOutMillis / portTICK_RATE_MS);   // ← 受超时约束
xSemaphoreGive(bus[i2c_num].lock);
```
锁本身是 `portMAX_DELAY`，但**持锁区间有界**，所以不会永久阻塞。

**真正的元凶是我上一版的"放宽超时"（又一次是我引入的）**
`waitready(timeout)` 是按 **10ms 步进空转**到超时的，每步还各含一次 I2C 事务：
```
单次 waitready ≈ 10 × (Wire 超时 + 10ms)
sendCommandCheckAck 调 2 次 waitready
RfidNfc::begin() 共 3 个命令（wakeup 内的 SAMConfig + getFirmwareVersion + 显式 SAMConfig）
⇒ 放宽到 100ms 时：≈ 7 秒 完全无响应 ⇒ 观感就是"卡死"
```
**关键事实**：ESP32 core 的 `_timeOutMillis` **默认就是 50ms**，
Adafruit 自己的 PN532 I2C 例程也用它、从未调过 ⇒ 50ms 对 clock stretch 是够的。
**"为了容忍 stretch 而放宽超时"是纯猜测，代价是把故障阻塞放大 4 倍。**

**修法**
1. `PN532_I2C_TIMEOUT_MS` **100 → 50**（= 板上常规值，等于取消放宽）。
   顺带把这一条实测结论写进 shared.h 的注释，防止以后又有人去"放宽"。
2. 新增 `RFID_PROBE_TRACE`（默认 1）+ `rfidProbeStep()`：在自检条下方 y=46 打一行
   `N/5 阶段名  t=xxxxms`，分 5 步卡点：
   `1/5 attach bus → 2/5 nfc.begin() → 3/5 getFirmwareVersion → 4/5 SAMConfig → 5/5 setPassive…`
   ⇒ 把"卡住"变成"卡在哪一次调用、已经耗了多久"。排查完置 0 即可去掉。
3. 复位后等待 60ms → **150ms**（芯片启动余量）。

**预期**：握手正常时探测 ≈ 50ms 级；异常时 ≈ 1.8s 后给失败结论 + 提示框（不再像卡死）。

### 🎯 用户回执（11:14）：内容半天不刷新、只有下面那条栏在动；读卡特别慢

**症状解读**：`statusBarTask` 是**独立 FreeRTOS 任务**（每 400ms 画一次），
所以主任务被阻塞时只有它会继续动 —— "只有那条栏在刷新"正是主任务被长时间阻塞的特征。

**根因：`setPassiveActivationRetries(0xFF)` = 无限重试**（原代码 5 处都这么写）
含义是 PN532 会**一直开着 RF 场反复轮询、直到找到卡才报"就绪"**。
没有卡时它**永远不就绪** ⇒ 连锁反应：

```
readPassiveTargetID(timeout=150) → sendCommandCheckAck → waitready(150)
waitready 按 10ms 步进 ⇒ 迭代 16 步
每一步的 isready() 都是一次 I2C 读；而 PN532 忙时会把 SCL 拉住（clock stretch）
⇒ 该读要等满 Wire 超时 50ms
⇒ 单次 readPassiveTargetID ≈ 16 × (50 + 10) ≈ 960ms
```
会话内每轮 UI 都要等这件事做完 ⇒ 界面约 1 秒才刷一帧，
且芯片一直"忙"，**后续每条命令的 isready() 也都得等超时** ⇒ "读卡特别慢"。

**修法（已编译 EXIT=0 / 1778877 B / 零告警）**
1. **`setPassiveActivationRetries` → `PN532_PASSIVE_RETRIES = 2`**（5 处全改）——
   让每条命令迅速返回"无卡"，芯片随即空闲。检测能力不受影响：
   上层本来就在 20s 窗口里反复调用。**这是本次主修。**
2. **`readPassiveTargetID` 的库内轮询超时 80 / 150 → `PN532_READ_POLL_TIMEOUT_MS = 40`**，
   给单次阻塞兜底。
3. **I2C 模式下 `rfidAttachBus()` 改空操作** —— 原来每进一个会话都重跑
   `s_nfc.begin() + SAMConfig() + setPassiveActivationRetries()`，那是 SPI 模式
   （bitbang 每次都要重挂总线）遗留的做法；I2C 下纯属多余，且每条命令几百 ms，
   表现为"进了会话半天不出界面"。

**一个反直觉但重要的结论**：I2C 从机**不存在**时是**立即 NACK**（毫秒级），
**不会**等满 `Wire` 超时 —— 所以 `0x75:--` 的轮询开销可忽略。
真正吃满超时的是**存在但忙 / 在 clock stretch** 的 PN532。
⇒ 以后遇到"慢"，要往"设备在但不应答或忙"方向查，而不是"设备不在"。

**待实机验证**：会话界面应流畅刷新（约 20Hz 级），贴卡检测仍正常。

### 🔬 用户回执（11:31）：进去快了，但读标签仍然很慢很卡 —— 改用测量代替猜测

**已排除的嫌疑（都查过源码）**
| 嫌疑 | 结论 |

**⇒ 剩下的只能是 PN532 命令本身。** 于是停止猜测，在监听循环里装**每帧计时探针**

```

```
- `P` = 上一次 `readPassiveTargetID` 的耗时
- `F` = 上一整帧的耗时

而库的 `isready()` 是 private。

**这一轮的教训**：连续四轮都在"猜 + 改"，从这一轮起改成"先量再改"。

## 六、"上电按键按不了" —— 根因：GPIO1 从未初始化（PN532 吊在复位态拖 I2C）

用户报：改完这版后上电，**按键按不了**；并猜测"是不是 I2C 有干扰，换 SPI 会不会好"。

### 根因（因果链）

```
GPIO1 从未被固件初始化（全工程零 pinMode(1,…)）
  ⇒ 用户接的 PN532 RSTPDN 上电后一直是高阻（对芯片 = 悬空）
  ⇒ PN532 停在复位态，扰动 I2C 总线
  ⇒ setup 里 initPcf8574Buttons() 的地址探测失败，s_pcf8574Addr 保持 0
  ⇒ isPhysicalButtonPressed() 开头就是
       if (getPcf8574Address() != 0) { ... }
       return false;
  ⇒ **五个按键全部恒返回"未按下"，而且屏幕上完全看不出异常**
```

**这是上一轮我要求用户把 RSTPDN 接到 GPIO1 时留下的坑**：我只在"进 RFID 功能"
时才 pulse 这个脚（`RfidNfc::hardwareReset()`），却忘了 setup 从不驱动它 ——
所以从上电到第一次进 RFID 之间，芯片一直吊在复位态。
反证：进一次 RFID 会 pulse 释放 → 总线恢复 → "按键又能用了"，用户之前看到的
`0x20:OK 0x24:OK` 正是**复位之后**测到的。

### 修法

| 文件 | 改动 |
|---|---|
| `shared.h` | 新增 `BOOT_RELEASE_PN532`(1)、`BOOT_I2C_SELFTEST`(1) |
| `utils.cpp` | 新增 `bootReleasePn532Reset()`：`pinMode(PN532_I2C_RST,OUTPUT)+HIGH+delay(5)` |
| `utils.cpp` | 新增 `bootI2cSelftest()`：扫 0x03..0x77 + **读 PCF8574 原始字节**，画屏幕停留 |
| `utils.h` | 两个声明（+ CYD 分支的空实现 stub） |
| `ESP32-DIV.ino` | `bootReleasePn532Reset()` 放在 **setup 第一件事**（早于任何 I2C 访问）；`bootI2cSelftest()` 放在 `initPcf8574Buttons()` 之后、`startStatusBarTask()` **之前**（否则那 2.5s 被状态栏任务覆盖） |

体检条异常时停 **6s**（正常 2.5s）—— 那种情况下这两行是唯一线索。

编译：`EXIT=0` 零告警，`Sketch 1779961 B (90%)`。

### 关键结论（沉淀）

1. **"按键全废"要先查 `getPcf8574Address()` 是否为 0**，而不是查按键逻辑 ——
   该函数为 0 时 `isPhysicalButtonPressed()` 直接短路，症状是"完全没反应"
   （区别于"读失败返回 LOW"造成的"恒按下、到处乱跳"）。
2. **"能 ACK" ≠ "能读数据"**：PCF8574 库在 I2C 读失败时保持旧缓冲值 →
   `digitalRead()` 返回 LOW（= 判定按下）。所以体检必须读原始字节：
   空闲应为非 0（正常 0xFF）；读到 `0x00` 只可能是"5 键同按"或总线被拖。
3. **上电即驱动 RSTPDN 是必须项，不是优化项** —— 凡是把 PN532（或任何需要
   外部复位释放的模块）接到一个"固件原本不碰"的引脚上，都要显式初始化它。

### 关于"换 SPI"（回答用户）

**不建议**，且不解决根因：
- 根因是"芯片吊在复位态"，与总线类型无关 —— SPI 模式下同样会不正常
- V2 上 SPI 路线本身有硬伤：CS 需独立脚（GPIO1 已被 RSTPDN 占用，只剩
  IO19/20 = 牺牲 USB-JTAG）；`PN532_MISO 11 / MOSI 13` 与共享总线
  （SD/CC1101 是 MISO 13 / MOSI 11）**方向相反**，只能 bitbang，
  而 bitbang 要占 11/12/13 → 与 SD/CC1101 同脚争用（正是当初改走 I2C 的原因）

## 七、"扫卡慢 + 触屏按键卡死 + 卡死后必须断电才能重启"（三个独立故障叠在一起）

用户报三条，实际是**三个不同原因**，逐条拆：

### ① "必须把电源关掉才能重启" = I2C 总线锁死（最严重）

I2C 有一个不对称的坑：**从机把 SDA 拉住不放时，主机复位解不开它。**
从机在传输中途被打断后会停在"还剩几位没吐完"的状态继续拉低 SDA；
此后主机发不出 START，每次事务只能吃满超时 —— 整机越来越慢直到卡死，
而且**按复位键重启无效**，必须给从机断电（它掉电才会松手）。
这正是用户描述的症状指纹。

**修法**：新增 `i2cBusRecover()`（utils.cpp）—— SCL 当普通 GPIO 打 **9 个时钟**
让从机吐完剩余位，再在 SCL 高时做 SDA 低→高的 **STOP**。
只在检测到"空闲态 SDA 为低"时才动手。
- `setup()` 里在 `bootReleasePn532Reset()` 之后、**Wire.begin() 之前**调一次
  ⇒ 这是"不用拔电源就能恢复"的软件手段
- 会话看门狗触发时也调一次

### ② "重启后屏幕也卡住" = **我上一版引入的**

`bootI2cSelftest()` 无条件全扫 0x03–0x77。总线坏时每个地址都吃满 50ms 超时
⇒ **117 × 50ms ≈ 5.9s**，再加 6s 停留 ⇒ 约 12 秒黑屏，被当成"死机"。
（我自己在 skill 里写过"总线死时先 ping 常驻器件、活着才全扫"，却没遵守。）

**修法**：体检条改成**带闸门** —— 先只 ping 板上常驻的 0x20：
- `0x20` 应答 ⇒ 才做全扫
- 不应答 ⇒ 直接报 `BUS STUCK - scan skipped`，**不扫**
另外显示 `SDA=x SCL=x` 静态电平（空闲应为 1；为 0 ⇒ 总线被从机拉着），
停留时间从异常 6s 收到 **4s**（总线坏时用户会把"等待"读成"死机"）。

### ③ "扫卡特别慢 + 触屏按键基本卡死" = 库的读卡是**阻塞式**的

读库源码确认：`readPassiveTargetID()` → `sendCommandCheckAck()` → `waitready()`
**按 10ms 步进空转**到超时；而 `readdata()`（`readDetectedPassiveTargetID` 里
无条件调用）**完全没有就绪检查**，直接读 21 字节。
按键和触摸都在主循环里轮询 ⇒ 每次读卡都把整个 UI 排在 I2C 后面。

**修法**：新增 `rfidPollTag()` —— 拆成「发一次命令」+「每帧只查 RDY 位」：
```
s_nfc.startPassiveTargetIDDetection()      // 发命令（ACK 很快，不阻塞）
  ↓ 之后每帧：
rfidI2cReadyBit()   // Wire 直读 1 字节 == 0x01 ？ 代价 ~几百 µs
  ↓ 只有 ready 才去读那 21 字节
s_nfc.readDetectedPassiveTargetID()
```
`rfidI2cReadyBit()` 自己实现（库的 `isready()` 是 private；
地址 `PN532_I2C_ADDRESS`=0x24、就绪值 `PN532_I2C_READY`=0x01，都是公开宏）。
自带两处自愈：命令超 `RFID_TAG_CMD_RETRY_MS`(1000ms) 没回音 → 丢弃重发；
`s_pollMs` 记录"命令已等了多久"，供看门狗判总线异常。
SPI 模式（非 V2）保持原阻塞调用不变。
> 保留一处阻塞调用：`rfidTagStillPresent()`（Dump 中每块确认卡还在不在），
> 它需要同步结论，非阻塞化反而没用。

### ④ 会话看门狗：不再让"卡死"成为死局

`rfidListenIso14443a` 里：`s_pollMs > RFID_BUS_STALL_MS`(700ms) 连续
`RFID_BUS_STALL_LIMIT`(3) 次 ⇒ `i2cBusRecover()` + 报 `[!] I2C bus stalled`
+ **主动退出会话**，把控制权还给界面。

### ⑤ 进 RFID 不再无条件复位

原来每次进功能都 pulse RSTPDN。但 PN532 正在工作时被突然复位，其 I2C 引脚
可能进到不确定状态**把 SDA 拉住** —— 也就是 ① 的成因之一。
改成：先 ping 0x24，在 ⇒ 别碰它；不在 ⇒ 才复位 + 解总线。
另外"能 ACK 但拿不到固件版本"时再复位重试一次（覆盖芯片陈旧状态）。

### ⑥ 新增可调项

| 宏 | 默认 | 用途 |
|---|---|---|
| `I2C_BUS_CLOCK_HZ` | 100000 | 外接模块走杜邦线时降到 **50000** 往往立刻变稳 |
| `I2C_BUS_RECOVER` / `I2C_SDA_PIN` / `I2C_SCL_PIN` | 1 / 8 / 9 | 总线恢复 |
| `RFID_BUS_STALL_MS` / `_LIMIT` | 700 / 3 | 会话看门狗 |
| `RFID_TAG_CMD_RETRY_MS` | 1000 | 命令无回音则重发 |
| `PN532_READ_POLL_TIMEOUT_MS` | 100（40 → 100） | 40ms 对 PN532 的 RF 轮询偏紧 |

### 仍然待定的一条

"扫卡慢"如果换完非阻塞轮询还明显慢，就要往**硬件**查（外接模块走杜邦线的
经典问题）：SDA/SCL 线太长 / 模块端上拉不足 / 模块 VCC 无就近去耦。
先试 `I2C_BUS_CLOCK_HZ = 50000`，再考虑在模块端加 4.7k 上拉 + 10µF 电容。

## 八、V2 最终从 I2C 改回 SPI（总线隔离）—— 2026-09-23 定案

### 定案依据（用户实测）

| 实测 | 结论 |
|---|---|
| **拔掉 PN532 模块就不卡** | 确认根因 = PN532 拖死共享 I2C 总线 |
| **卡死后仍需断电** | 我上一版的 `i2cBusRecover()` **没生效** |

**为什么没生效**：旧判据只查了 `digitalRead(SDA) == HIGH` 就 return false，
**而 PN532 卡住时拉低的往往是 `SCL`**（clock stretch 不释放）—— 那种情况下
SDA 仍是高，恢复流程根本没被触发。**这是判据不全的 bug，两条线都要查。**
已改成 `if (!sdaLow && !sclLow) return false;`，`bootI2cSelftest()` 里的触发条件
同步改成 `|| !sclIdle`。

> 这也是本次改 SPI 的根本理由：**不是 I2C 不行，是"把会闹脾气的模块和
> 键盘/PMIC 挂在同一条总线上"这个架构不行**。换 SPI 后 PN532 走自己的 4 根线，
> 就算再出问题也只影响 RFID 功能内部。

### 配置变更（`shared.h`）

| 宏 | 旧 | 新 | 说明 |
|---|---|---|---|

## 九、SPI 模式报"没找到设备"—— 代码侧核查 + 裸 SPI 诊断（待用户回执）

### 先确认：确实是 SPI

符号表 `rfid.cpp.o` 只有
`U Adafruit_PN532::Adafruit_PN532(unsigned char, unsigned char, unsigned char, unsigned char)`
（4 个 `unsigned char` = bitbang 构造），`TwoWire*` 构造与 `Adafruit_I2CDevice` 均已消失 ✓

### 库的 SPI 实现核查（把 Adafruit_BusIO 读透了）

| 事实 | 结论 |
|---|---|
| `Adafruit_SPIDevice(ss, clk, miso, mosi, 1000000, **SPI_BITORDER_LSBFIRST**, SPI_MODE0)` | 库给 PN532 配的是 **LSB first**，而且 `transfer()` 里**真的按 `_dataOrder` 移位**（`startbit = 0x1` vs `0x80`）⇒ **自己写诊断必须也用 LSB，否则读出来整个反了** |
| 头文件 `int8_t _irq = -1, _reset = -1, _cs = -1;` | **有默认值** ⇒ `reset()` 里 `if (_reset != -1)` 不成立、被跳过 ⇒ 不会误动 GPIO0(TFT_RST)。（曾担心 4 脚构造没初始化 `_reset` 会把 GPIO0 拉低，已排除） |
| `Adafruit_SPIDevice::begin()` 的 `else`（bitbang）分支 | `pinMode(sck,OUTPUT) + digitalWrite(sck,LOW) + pinMode(mosi,OUTPUT) + pinMode(miso,INPUT)`，**返回 true** ⇒ 不是卡在这里 |
| `Adafruit_PN532::begin()` | `spi_dev->begin()` → `reset()` → `wakeup()`（SPI 分支只做 `CS低+delay(2)`）→ `SAMConfig()`。**它返回 true 不代表芯片在**，真正判据是 `getFirmwareVersion()` ✓ 代码逻辑本来就对 |

⇒ **代码侧没找到"必然失败"的点**，怀疑落在接线侧。

### 本轮新增的两处加固

1. **`rfidSpiRawStatus()`**（ESP32-DIV.ino）：绕过库、直接 bitbang 读
   `StatusRead(0x02)`，失败时把原始字节打到自检条上。判读：
   | raw | 含义 |
   |---|---|
   | `01` | 芯片活着且 ready ⇒ 接线是对的，问题在库调用/时序 |
   | `FF` | MISO 恒高 ⇒ 没供电 / SEL 不在 SPI 档 / MISO 没接 |
   | `00` | MISO 恒低 ⇒ **CS 与 RSTPDN 还并在一起**（头号嫌疑）/ 短路 |
   | 其它 | MISO/MOSI 可能接反 |
2. **`rfidQuiesceSharedBus()`**（rfid.cpp）：进入会话前显式拉高
   `CC1101_CS` / `SD_CS`。bitbang 在 GPIO11/12/13 上直接推信号，
   只要有一个器件的 CS 还停在低，它的 MISO 就会来争这根线 ⇒ 连 StatusRead
   都读不到。（原来只有"退出时"的 `restoreSdAfterSharedSpi()`，进入时没人管。）

编译 `EXIT=0` 零告警，`Sketch 1781385 B (90%)`。

### 交给用户的 4 个必查点（按可能性排序）

1. **RSTPDN 是否已从 GPIO1 拆走**（若与 CS 并接：每次 CS 有效都同时复位芯片）
2. **SEL 开关是否拨回 SPI/HSU 档**（之前为 I2C 拨过去过）
3. **MISO/MOSI 是否交叉接**（代码期望 PN532 MISO→11、MOSI→13，与板上同名网络相反）
4. **CS 是否接在 GPIO1**
决定性测量：**万用表量模块 RSTPDN 对 GND 应为 3.3V**；若为 0V 或跳变 ⇒ 芯片在被复位。

### 用户实测：`raw=0xFF`（MISO 恒高 = 该线没人驱动）

`0xFF` 只说明"MISO 上没有任何器件在拉低它"，但**背后有 6 种完全不同的原因**，
修法各不相同。已把诊断升级为**同一根线测两种引脚映射**（`rfidSpiRawStatusPins()`），
一次烧录就能自己分开：

```
N = 正常组合(SCK12/MISO11/MOSI13/CS1)
S = 交换组合(SCK12/MISO13/MOSI11/CS1)
```
| N / S | 结论 | 修法 |
|---|---|---|
| N=01 | 芯片活着 | 问题不在接线，继续查库/时序 |
| **S=01** | **MISO/MOSI 接反了** | 把 11/13 两根线对调 |
| N=S=FF | MISO 没人驱动 | SEL 档位 / 模块 VCC / CS 没接对 / MISO 线断 |
| N 或 S=00 | MISO 被拉住 | CS 与 RSTPDN 并接、线短路 |

`0xFF` 的 6 个候选原因（按可能性）：
1. **SEL 开关不在 SPI 档**（之前为 I2C 拨过去过）
2. **MISO 接在 GPIO13**（交叉接法容易接成同名对齐）← 新诊断能测出
3. **CS 没接在 GPIO1**（若 CS 一直为高，PN532 永不被选中 ⇒ MISO 高阻）
4. **模块 VCC 没供上**
5. **RSTPDN 没拉高**（芯片在复位态，MISO 也是高阻）
6. MISO 线断 / 没插到底

编译 `EXIT=0` 零告警，`Sketch 1781505 B (90%)`。

## 十、RFID 最终解决：MISO/MOSI 接反（用户手工交换后完全正常）

### 结论

用户仔细复查后**把 MISO 和 MOSI 对调，问题消失**，且**读取速度比 I2C 快得多**。

- 与诊断判读**完全一致**：`raw=0xFF` + 对调后可用 = "接反了"那一类
- **代码无需改动**：`shared.h` 的 V2 定义本来就是
  `PN532_SCK 12 / PN532_MISO 11 / PN532_MOSI 13 / PN532_SS 1`
  —— 用户对调后的接法正好与之一致
- 用户没编译"双映射诊断"那一版（已经不需要了）

### 最终接线（定案，以后不用再试）

| PN532 | 接板 |
|---|---|
| SCK | GPIO12 |
| MISO | **GPIO11** |
| MOSI | **GPIO13** |
| CS | GPIO1（原 WS2812 焊盘） |
| RSTPDN | **3V3 经 10k 上拉**（固件不驱动，`PN532_I2C_RST = -1`） |
| SEL | **SPI 档** |
| IRQ | 不接 |

**为什么是交叉的**：板上共享总线（SD/CC1101）是 `SCLK 12 / MISO 13 / MOSI 11`，
而代码给 PN532 定的是 `MISO 11 / MOSI 13` —— **两者正好互换**。
按"同名对齐"接必错，这是本次绕了好几圈的根因。

### 传输方式：确认是**软件 SPI（bitbang）**

`Adafruit_PN532(clk, miso, mosi, ss)` 4 参数构造 → `Adafruit_SPIDevice(ss, sck, miso, mosi, ...)`
4 脚构造 → **不设 `_spi`**，`begin()` 走 `else` 分支 `pinMode/digitalWrite`，
通信全靠 GPIO 位操作 ⇒ **不占硬件 FSPI 外设**（这正是原设计要的：
避开与 SD/CC1101 的总线争用）。
速度约 400kHz~1MHz（受 GPIO 翻转限制），但**全双工 + 无 ACK + 无 clock stretch**，
实际比 100kHz 的 I2C 快得多 —— 与用户"快得多"的实测吻合。
想更快可换硬件 SPI（1~5MHz），但要接 FSPI、需严格 CS 管理，**不建议**。

| `RFID_PROBE_TRACE` | 1 → **0** | 不再显示 P=/F=（但 `s_pollMs`/`s_frameMs` 仍统计，会话看门狗要用） |
