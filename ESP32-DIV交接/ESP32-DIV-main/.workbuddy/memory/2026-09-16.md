## GPS（ATGM336H）接入可行性分析（09:04）

用户想用中科微 **ATGM336H**（手册推荐串口，也说可用 I2C），问工程还有没有多余串口。

### 工程侧现状

- GPS 走 **UART2**（`gps.cpp:28 #define GPS_UART_NUM 2`）、波特率 **9600**（`GPS_UART_BAUD`），
  用 `HardwareSerial gpsSerial(2)` 读 NMEA（`gpsSerial.available()/read()`，`gps.cpp:586-587`）。
- ESP32-S3 有 **3 个 UART**（core `HardwareSerial.cpp` 里 `#if SOC_UART_NUM > 2` 成立）；
  工程中 `Serial`(UART0) 用于调试/串口终端，**UART1 完全空闲**（全工程无 Serial1/Serial2 引用）。
- **关键：ESP32 的 UART 引脚可由 GPIO matrix 任意映射** ⇒ 真正的瓶颈是 **GPIO 数量**，不是 UART 控制器。

### 致命冲突（V2 默认 GPS 引脚全被 CC1101 占了）

| 宏 | V2 值 | 撞谁 |
|---|---|---|
| `GPS_UART_RX` | **5** | **`CC1101_CS` (GPIO5)** |
| `GPS_UART_TX` | **6** | **`SUBGHZ_TX_PIN` / `CC1101_GDO0` (GPIO6)** |

⇒ GPS 在 V2 上「开箱即用」不可能，**必须改引脚**。

### ATGM336H-5N 手册要点（已查证）

- 引脚：2=TXD、3=RXD、4=1PPS、5=ON/OFF、6=VBAT、8=VCC(3.3V，峰值 100mA)、9=nRESET、
  11=RF_IN、14=VCC_RF(给有源天线供电，50mA 限流)、**16=SDA、17=SCL**；
- ⚠ **16/17 在官方手册 pin 表里标注为「悬空」，且全手册无 I2C 协议/寄存器说明**
  ⇒ 硬件虽有 I2C 引脚但**无文档支持**，实用价值低，**不推荐走 I2C**；
- 默认 UART **9600** 8N1，NMEA0183；速率范围 4800~115200；定位更新率默认 1Hz（最高 10Hz）；
- 电平：官方手册 `Vin: −0.3 ~ Vcc+0.2`（3.3V 供电 → 最高 3.5V）、`Vih = 0.7×Vcc = 2.31V`
  ⇒ **3.3V MCU 电平兼容**；建议 MCU-TX → 模块-RXD 串 **1K 电阻**保险。
  （网文有「1.8V TTL」说法，与该手册参数不符，以手册为准、实测确认）
- 对电源纹波敏感（建议 10µF 钽 + 0.1µF 陶瓷就近放置）；**VBAT 接后备电池/超级电容
  （1.5~3.6V，10µA）⇒ 热启动 ≤1s**（不接则每次冷启动 ≤35s）。

### 推荐方案

**UART + 换引脚到空闲 GPIO**（控制器可用 UART1，或继续用 UART2）：
- V2 当前空闲 GPIO：**24 ✓ / 41 ✓ / 42 ✓**（41/42 = JTAG MTDI/MTMS，eFuse 默认不占）；
  GPIO1 若留给 WS2812 则不可占用；
- 建议 `GPS_UART_RX = 24`、`GPS_UART_TX = 41`（或 42）。

**待用户确认**：复刻板上 GPS 排针/焊盘实际走线到哪个 GPIO —— 决定是改代码还是改硬件。

## ⚠ 勘误 + 冲突复核（09:20）

`SOC_GPIO_VALID_GPIO_MASK = 0x1FFFFFFFFFFFFULL & ~(0ULL | BIT22 | BIT23 | BIT24 | BIT25)`
⇒ S3 只有 GPIO0–21 + 26–48，**22/23/24/25 无焊盘**。凡涉 S3 空闲引脚，禁用 22–25。

**V2 固件层面真实空闲 GPIO：39 / 41 / 42**（原建议 24 作废；**33/34 也已作废，见下**）。

> ⚠ **第二次勘误（10:40，用户告知模组是 ESP32-S3-WROOM-1）**：
> **GPIO33 / GPIO34 在 WROOM-1/1U/2 模组上根本没有引出焊盘**（裸片有，模组没有）；
> 且在八线 PSRAM 版本里它们被内部八线接口占用，软件里误配会碰到内部 PSRAM/flash 线、
> 可能把 PSRAM 锁死或直接崩。**所以 33/34 一条都不能用。**
> 依据：atomic14「ESP32-S3 Pinouts」+ 中文模组引脚表（"GPIO33、GPIO34 未引出"）。
> ⇒ 这块板真正可用的空闲脚只有 **39 / 41 / 42**（另加 GPIO1，若不用 WS2812）。
> 当时最终选的 41/42 没问题，但"备选 33/34"是错的。
- 19/20 = USB D−/D+；26–32 = 内部 SPI Flash；45 = strapping；0/46 = strapping；43/44 = Serial(UART0)。
- 40 已被 IR_RX 占用；41/42 = JTAG MTDI/MTMS，USB-JTAG 方案下可作普通 IO。

### 用户提出「GPIO5/6 给 GPS 串口，因为 CC1101 只用 SPI，SPI 不操作就没事」

**判定：不成立。** GPIO5 不是 SPI 数据线，是 CC1101 片选，由 ESP 主动 `pinMode(OUTPUT)` 驱动；
GPIO6 = `SUBGHZ_TX_PIN` = `CC1101_GDO0`，是 Replay/Brute 时 ESP 高速翻转的发射调制脚。
致命点在于 **GPS 模块上电即按 1Hz 持续吐 NMEA，物理上永远挂在 GPIO5 这跟线上**：
- GPIO5 上任何 NMEA 跳变对 CC1101 就是随机片选脉冲 → SPI 不操作也会被误写；
- GPS TX 与 ESP GPIO 均为推挽输出，同网直连存在对灌电流风险；
- 唯一「共用」前提是 GPS VCC 可被 MOSFET 开关且断电后 TX 高阻 —— ATGM336H 小板不满足，不推荐。

`gps.cpp` 里有 `gpsSerial.end()`（26 处），走的是 `HardwareSerial::end(fullyTerminate = true)`
→ `uartDetachPins()`，退出后引脚会归还 GPIO，所以**不存在"引脚被 UART 永久劫持"的问题**；
问题纯粹是硬件常连通，软件无法分时。

**待办**：用户决定实际焊到哪对脚后，改 `shared.h` V2 分支
`GPS_UART_RX`（现 5）/ `GPS_UART_TX`（现 6）→ 建议 41/42，并编译验证。

## GPS 面板"有时候缓冲失败"诊断 + viewport 降级直绘（10:15）

用户报"有时候会缓冲失败"（即 `Display buffer failed` 死屏，`createSprite` 失败）。

### 机制（已查证库源码）

- `TFT_eSprite::callocSprite` 用的是**普通 `calloc`**；`#if defined(CONFIG_SPIRAM_SUPPORT)`
  分支在本构建（PSRAM=disabled）**根本没编进去** ⇒ 只能从内部 SRAM 取**连续**块。
- 需求：8bpp 240×298 = **71,520 B**（+1）；16bpp = **143,040 B**。循环内层是先 8bpp
  ⇒ **平时就跑在 8bpp（RGB332 / 256 色，颜色被量化）**，不是 16bpp。
- 内部 SRAM 静态已占 135 KB / 320 KB，剩堆 ~190 KB。跑过 WiFi 扫描 / BLE 等吃大块堆的
  功能后堆碎片化 ⇒ 71.5 KB 连续块间歇性拿不到 ⇒ "有时候"。**与"之前进过哪个功能"强相关**。
- 另注：`sessions` 退出时**故意不 deleteSprite**（gps.cpp:1314 有注释），就是为了避免
  释放后碎片化导致再次进入分配失败。

### 改动（全部在 `gps.cpp`）

1. `ensureScanPanelSprite`：高度步长 18→**6**（34 次尝试），`delay(20)`→**5 ms**
   （calloc 失败是立即返回，delay 只为让出 CPU；最坏耗时反而 240→170 ms）。
2. `redrawFeaturePanel`：
   - 拿不到缓冲**不再显示 "Display buffer failed" 死屏**，改为 **viewport 降级直绘**：
     ```cpp
     tft.setViewport(0, kGfxTop, tft.width(), tft.height() - kGfxTop, true);
     renderPanelGx(tft);
     tft.resetViewport();
     ```
   - 重试退避：连续失败 3 次后 800 ms → **5 s**（否则每 800 ms 就做几十次
     createSprite+delay，降级模式被卡成幻灯片）。
3. 新增受 `DIAG_PRINTS_ENABLED` 控制的诊断：成功/失败都打印 sprite 尺寸、需求字节、
   `ESP.getFreeHeap()`、`heap_caps_get_largest_free_block(MALLOC_CAP_8BIT)`。
   需 `#include <esp_heap_caps.h>` —— **Arduino.h / esp32-hal.h 都不带它**。

### viewport 降级为什么成立（逐个核对 TFT_eSPI 2.5.43 源码）

- `setViewport` 设 `_xDatum/_yDatum`（坐标偏移）+ `_vpX/_vpY/_vpW/_vpH`（裁剪），
  且 `width()`/`height()` 在 `_vpDatum` 时返回**视口**尺寸 ⇒ `renderPanelGx(tft)`
  拿到的就是 240×298 的面板坐标系。
- `fillScreen(color)` 实现是 `fillRect(0,0,_width,_height,color)`，经 `_xDatum` 偏移 +
  裁剪后**只清面板区**，不会擦状态栏。
- 面板用到的原语全部遵守偏移：fillScreen/fillRect/drawRect/drawRoundRect/drawCircle/
  fillCircle/drawLine/fillTriangle/drawString/drawChar/drawPixel
  （drawRect、drawRoundRect、fillCircle、fillTriangle 是间接经 drawFastHLine/drawCircleHelper 生效）。
- 面板路径里**没有** `drawBitmap`（那 9 处都在 wardriver 屏，那条是直绘 tft）。
- 代价：每 450 ms 整屏重绘会闪一下（原 sprite 路径就是为了消这个闪）。

- 生效的 `tools/sdk/esp32s3/qio_qspi/include/sdkconfig.h` 里只有
  `CONFIG_ESP32S3_SPIRAM_SUPPORT 1` / `CONFIG_SPIRAM 1` / `CONFIG_SPIRAM_USE_MALLOC 1`，
  **`CONFIG_SPIRAM_SUPPORT` 出现 0 次**；
- 而 `TFT_eSPI-master/Extensions/Sprite.cpp:165/181/192/209` 四处 `ps_calloc` 分支
  的条件都是 `#if defined (ESP32) && defined (CONFIG_SPIRAM_SUPPORT)`
  ⇒ **这些分支从来没被编译进固件**，开 PSRAM 也不会让 sprite 进 PSRAM。
- TFT_eSPI 那两行 `_psram_enable` / `psramFound()` 是**条件为真时才有意义**的代码。

**但开 PSRAM 仍然有实质收益**，机制是 `CONFIG_SPIRAM_USE_MALLOC=1`：
大于 `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`(4096) 的 `calloc` 在内部 SRAM 不够时
**回落到 PSRAM**，于是 71.5 KB 的 sprite 缓冲不再和 WiFi/BLE 抢内部堆；
再叠加 `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=1`（WiFi/LWIP 大缓冲也可进 PSRAM）。
⚠ 但这会让 sprite 缓冲变成 PSRAM 指针 —— 本工程 TFT 未启用 DMA
（User_Setup 无 `USE_DMA_TO_TFT`），故安全。

### 板子到底有没有 PSRAM：看模组丝印第二行

| 丝印后缀 | PSRAM | 能否用 |
|---|---|---|
| `N4` / `N8` / `N16` | 无 | 没得开，只能靠内存策略 |
| `N4R2` / `N8R2` | 2 MB **四线** | ✅ `PSRAM=enabled`（QSPI PSRAM） |
| `N8R8` / `N16R8` / `N32R16V` | 八线 | ❌ **不可能是这块板**：八线占 GPIO35/36/37，而 TFT 正在 35/36/37 上正常工作 |

⇒ 只剩"无 PSRAM"或"R2 四线"两种可能。IDE 选项名（core 2.0.9）：
`PSRAM=disabled`（无 defines）/ `PSRAM=enabled`（label "QSPI PSRAM"，`-DBOARD_HAS_PSRAM`，
psram_type=qspi）/ `PSRAM=opi`（"OPI PSRAM"）。
注意 enabled 与 disabled 都是 `psram_type=qspi` ⇒ 用的是同一个预编译库目录 `qio_qspi`，
切换只是加/去 `-DBOARD_HAS_PSRAM`。

### 已加验证手段

`ensureScanPanelSprite` 的 DIAG 行已追加 `psram=free/total`：开了 PSRAM 才会非 0；
若 `largest`（内部最大连续块）从几万跳到十几万，说明 71.5 KB 确实被 PSRAM 接手了。

### 若无 PSRAM：还剩一条结构性优化（未做，待用户决定）

## 面板高度降级导致布局歪 + 信号测绘被饿死（10:30）

## ✅ 方法 1 落地：离屏缓冲改为「纵向分带」分配（11:00）

用户选了"面板拆两块 sprite"的方案；实现时做成 **1 → 2 → 4 条带的阶梯**（比固定 2 条更稳，见下）。

### 为什么要阶梯而不是固定 2 条

把一块刚好 71.5 KB 的连续块切成两块 35.8 KB 时，malloc 的块头开销会让总需求略超原块 ⇒
**当"最大连续块刚好够一整块"时，两块反而可能分不到**。所以先试 1 条（与原行为一致、
不劣化），失败才细分：细分只在"一整块拿不到"的场景里发挥作用，严格优于原来。

### 实现要点（`gps.cpp`）

- 4 个静态 `TFT_eSprite`（`gScanBand0..3`）+ 指针数组 `gScanBand[]`，
  `kScanMaxBands = 4`，配 `gScanBandCount / gScanPanelW/H / gScanBandY[] / gScanBandH[]`。
- `releaseScanBands()` / `allocScanBands(n, panelW, panelH)` /
  `ensureScanBands(panelW, panelH)`；`allocScanBands` 按 `base + (i < rem ? 1 : 0)`
  切分，**总和精确等于 panelH**（298 → 149+149 或 75+75+74+74）。
- 全部 8bpp（8bpp 是既有行为，且只要一半内存）。
- 渲染：每条带
  ```cpp
  sp->setViewport(0, -gScanBandY[i], PW, PH, true);
  renderPanelGx(*sp);
  sp->resetViewport();
  sp->pushSprite(0, kGfxTop + gScanBandY[i]);
  ```
- `redrawFeaturePanel` 里删掉了"sprite 比面板矮就补黑"的分支（分带总和恒等于 panelH）。
- `pollViewNavigation` 的 `PH` 改为恒定 `tft.height() - kGfxTop`。

### 为什么「整面板坐标 + 每条带裁剪」能成立（逐条核对 TFT_eSPI 2.5.43 源码）

1. `TFT_eSprite` **没有重写** `setViewport` ⇒ 用的是 `TFT_eSPI::setViewport`；
2. `TFT_eSprite::width()/height()` 里有 `if (_vpDatum) return _xWidth / _yHeight;`
   ⇒ 设了 viewport 后返回的是**我们传进去的面板尺寸**（240×298），
   于是 `renderPanelGx()` 在每个带里都按同一套完整布局绘制（**不需要改它的签名**）；
3. `setViewport` 对负 y 做 `if (y < 0) { h += y; y = 0; }`，再 `if ((y+h) > height()) h = height() - y`
   ⇒ 传 `y = -bandY` 时裁剪区正好是 `[0, bandH)`，面板坐标 `bandY..bandY+bandH` 落在其中，
   带外（含负坐标）被丢弃；**跨带图元会在相邻两带里各画一半 ⇒ 分界线无接缝**；
4. 各原语都遵守 `_xDatum/_yDatum` 与 `[_vpX,_vpY,_vpW,_vpH]` 裁剪：
   `drawPixel / fillRect / drawFastHLine / drawFastVLine / drawChar / drawLine` 是
   `TFT_eSprite` 自己重写的；`drawRect / drawRoundRect / fillRoundRect / drawCircle /
   fillCircle / fillTriangle / drawString / fillScreen` 没重写，但**基类实现内部调用的是
   virtual 的 `drawPixel/drawFastHLine/fillRect`** ⇒ 动态分发落到 sprite 的实现上，同样遵守 viewport。
   `fillScreen()` 内部是 `fillRect(0,0,_width,_height)`（基类成员 = 240×320），
   经偏移+裁剪后正好铺满整条带 ✓
5. `TFT_eSprite::fillRect` 对负 `_yDatum` 的处理已核对（先 `y += _yDatum` 再裁剪）。

## "卫星扫描还是会闪屏"——成因分类与判定指纹（11:15）

### 结论：能看见的"闪"只出自**降级直绘**这一条路

- **分带推屏路径不会闪**：`pushSprite` 把缓冲内容写到屏幕，内容没变的位置是写同色像素，
  肉眼不可见；面板内容 1 Hz 才更新（NMEA），450 ms 重绘并不产生可见变化。
- **降级直绘（`renderPanelGx(tft)`）必闪**：它开头就是 `fillScreen(FEATURE_BG)`，
  整块面板先被清成底色、再重画 ⇒ 每次都是一次**可见的空白闪现**，频率 = 刷新周期
  （原来是 450 ms，即每秒闪两次多）。
⇒ 用户报的闪屏 = 该系统当下走的仍是直绘。两种可能：
  (a) 烧的还是**分带改造之前**的构建；

### 判定指纹（一眼区分新老构建 / 走哪条路）

| 输出 | 含义 |
|---|---|
| `[GPS] scanPanel sprite …` | **老构建**（分带之前），会闪 |
| `[GPS] scan bands 1 × 298px …` | 新构建 · 走离屏（不闪，最优） |
| `[GPS] scan bands 2 × 149px` / `4 × 75px` | 新构建 · 分带生效（也不闪） |
| `[GPS] scan bands alloc FAILED … -> direct-to-TFT` | 新构建 · 仍然直绘（会闪），并给出 heap/largest |

### 顺手做的缓解

降级直绘时把刷新周期从 450 ms 拉到 **1500 ms**（`kRedrawMsFallback`，

注意没有去掉直绘里的 `fillScreen`：去掉能进一步减少"空白闪现"，但会留下残影
（消失的卫星点 / 变短的数值），权衡后保留清屏、只降频。

## 【根因定论】卫星扫描整块闪屏 = 离屏缓冲分配失败（11:53 用户回传串口）

### 决定性数据（用户串口原文）

```

[ble] init done,  free heap=141772      ← 开机 BLE 初始化吃掉 51128 B
```

推算：

| 状态 | 分配前 heap | largest | 结果 |
|---|---|---|---|
| 开机后（BLE 已 init，未跑 WiFi 类功能） | 54812 + 71520 ≈ **126 KB** | — | 1 档满高**成功** → 不闪 |

（最可能是**信号测绘**：`WiFi.mode(WIFI_STA)` + 扫描；退出只 `disconnect()`，
**没有 `WiFi.mode(WIFI_OFF)`**，栈内存不还）。

### ⛔ 我上一轮的方案是错的（已废弃）

"把面板切成 N 条、N 条各分配一块"（**N 块并存**）——
切得再细，**总需求仍是 71.5 KB + N 份块头**，只是块变小。对"总量不足"完全无效：

- 2 档要两块 35760，`largest=51188` 只够切出 1 块 ⇒ 败

**教训：分片只解决"碎片"，不解决"总量"。容量不足时必须让"同时在手的缓冲"变小，

## GPS 星座识别修复：BD talker + GSA System ID（16:57）

用户实测反馈："搜到很多**蓝色和白色**的信号，蓝色下面写着 GPS，白色的不知道是什么"。

**判定成立**：蓝色/青色 = `baseColorForSystem(SYS_GPS)=0x07FF`；
白色/浅灰 = `baseColorForSystem(SYS_UNK)=LIGHT_GRAY`（图例里没有对应色块）。
⇒ **ATGM336H 用 `$BDGSV` 表示北斗**（不是 `$GBGSV`），而 `talkerSystem()` 只认 `GB`。

### 改动 1：`talkerSystem()`（gps.cpp:251）补 `BD`

```cpp
if (c1 == 'B' && c2 == 'D') return SYS_BDS;   // 北斗老式 talker，中科微模块默认
```
修后：北斗星变**橙色**（BDS 色）、SNR 标签由 `?05` 变 `BDS05`、图例 `BD` 色块能对上。
**隐形收益**：`handleGsvSentence()` 里的 `purgeConstellation()` 只在 `sys != SYS_UNK`
时执行 ⇒ 修之前北斗条目**只增不减**（会一直堆到 48 条上限，已消失的星也不消失）。

### 改动 2：`handleGsaSentence()` 解析 NMEA 4.10 的 System ID（顺带修的）

NMEA 4.10 的 `$GNGSA` 末尾多一个 System ID 字段（1=GPS 2=GLO 3=GAL 4=BDS 5=QZS），
4.0 老固件没有。原代码 `dopBase = nf - 3` 在带 System ID 时会落到 HDOP/VDOP 上：

1. **DOP 卡片的 H/P 数字错位**（PDOP 位显示 HDOP、HDOP 位显示 VDOP）；
2. **PDOP 的数值被当 PRN** 送进 `markSolution()` ⇒ 天空图白圈误标；
3. `$GNGSA`（talker=GN）被当 `SYS_GPS` ⇒ 北斗星的白圈全落到 GPS 行。

新判据（不会误判）：`nf >= 19` 且末字段是**单个数字 1..7**（旧格式字段数固定 18，
且 VDOP 一定是带小数的值）⇒ 视为 System ID，则 `dopBase = nf - 4` 并按 System ID
把 sys 归到正确星座。

`gps.cpp:3681 wardStartBackground()` —— 在**信号测绘页底部工具栏**点"后台运行"后，
启动 `wardBgTask`（后台继续扫描并写 CSV），成功时弹这条确认。同一个函数还有另外三条：
`Background run already active.` / `SD required for background log.` /
`Could not start background task.`

### 真正的两个问题（都已修）

**问题 1：弹窗不会自动消失 —— 必须手动点一下。**

根因：`utils.cpp` 里 `notificationVisible = false` **只**出现在 `hideNotification()` 中，
而 `hideNotification()` **只**由 `notificationHandleTouch()` 调用 ⇒ 纯模态、无超时。
更糟的是信号测绘的循环（`gps.cpp:3913`）遇到通知会 `continue` **吞掉所有输入**，
所以弹出后整页卡在等触摸的状态。

修法（一处改动覆盖所有页面）：
```cpp
static uint32_t s_notifShownMs = 0;
static constexpr uint32_t kNotifAutoHideMs = 6000;
// drawNotificationInternal() 末尾记录 s_notifShownMs = millis();
void notificationTick() {           // 无 Save 按钮的提示 6 s 后 hideNotification()
  if (!notificationVisible || notificationHasSave) return;
  if ((uint32_t)(millis() - s_notifShownMs) >= kNotifAutoHideMs) hideNotification();
}
bool isNotificationVisible() {      // ★ 关键挂载点
  notificationTick();
  return notificationVisible;
}
```
- **为什么挂在 `isNotificationVisible()` 里**：所有功能页的模态等待都写成
  `if (isNotificationVisible()) { …等触摸… }`，而功能页有自己的 while 循环**不走 `loop()`**；
  挂这里一次覆盖全部页面（信号测绘 / wifi / bluetooth / subghz / 主菜单）。
- `ESP32-DIV.ino` 的 `loop()` 里另加一行 `notificationTick();`（语义明确）。
- `notificationHasSave`（带 SAVE 按钮的确认框）**不自动消失**，仍需用户决定。

**问题 2：这 20 条通知文案全是英文**（`gps.cpp` 里 `wardNotify`/`showNotification` 的
message 走 `uiPrint` 本来会翻译，但一条都没进翻译表）。已补齐：

- 词条 611 → **635**，字形 429 → **449**，字库 **22450 B**（12×12 8082 + 16×16 14368）。
- 提取方式：脚本直接从 `gps.cpp` 抓字符串并**合并 C 语言的跨行字面量拼接**
  （`"a" "b"` → `"ab"`），再按原文当 dict key 配对译文 —— 保证键与运行时串逐字节一致。
  注意那条 WiGLE 长提示里含 `—`(U+2014) 和 `Wi-Fi` 的 U+2011 非断行连字符。
- 代表译文：`Running in background. Open Wardriver to stop.` → 「已转入后台运行，回到信号测绘可停止。」

### 顺带：后台任务收尾也不关 WiFi

`wardBgTask` 尾部原来只 `WiFi.disconnect()`（和前台 session 一样的问题）⇒ 停掉后台测绘后
WiFi 仍占 30~50 KB。已改成 `WiFi.disconnect(true, false)`（第一参数 true → 内部走
`WiFi.mode(WIFI_OFF)`；第二参数 false → 不擦 NVS 凭证）。
至此三处收尾（前台 session / 后台任务 / 卫星扫描）都会归还 WiFi 内存。
