## 冷启动色块全空、插 USB 才亮（重要回归，已修复）
- 现象：纯电池冷启动，色块一直空（等多久都不行）；插 USB 亮、拔掉后保持亮。
- **根因（我上一轮 batteryDisplayPercent 引入的 bug）**：`batteryDisplayPercent()` 首次调用时 `if(s_disp<0){s_disp=raw;return raw;}`。冷启动前 5s `readBatteryVoltage()` 返回 0 → `raw=0` → **s_disp 被锁成 0**；之后电压采到真实值(如 40%)，但 s_disp 已非 -1，进入"放电只减不增"分支 `raw<=s_disp-1` 不成立 → 真实值被当"反弹"吞掉 → **s_disp 永远 0 → 色块空**。插 USB 进入"充电只增不减" `raw>=0` 成立 → s_disp=40 → 亮；拔后保持 → 正常。与现象完全吻合。
- **修复**（utils.cpp `batteryDisplayPercent` 内，`if(s_disp<0)` 前）：`if (voltage <= 0.01f) return s_disp;` —— 电压未测到时不初始化 s_disp（保持 -1 未就绪），首次拿到有效电压才用真实值初始化。改动仅此一处。
- 教训：状态机类迟滞的**首次初始化必须以"输入有效"为前提**，不能用无效输入(0)灌状态。

- 用户烧录 5000/2500 回退版后仍"纯电池冷启动色块不亮、等 1 分钟不行、插 USB 才亮"。**2s 时序假设被证伪**——源码理论上已与之前"可以了"的版本一致。
- 两个待排除方向：① 用户烧的不是当前源码的产物（陈旧 bin/IDE 缓存）；② ADC 读取本身与供电状态相关（纯电池时永远采不到有效值）。
- 行动：`shared.h` `SCREEN_DEBUG` 0→1，用 statusBarTask 每 3s 的 `[IP5306] ... Vbat=%d src=%c adc=%dmV` 行（utils.cpp:1380，adc=s_adcProbeMv=IO2 原始 mV）取运行时数据。判读：绿字完全不出现=陈旧 bin 或 loop 没跑；有行但 adc≈0/乱值=ADC 供电态问题；adc≈1810 而 Vbat=0=窗口/流程问题；Vbat≈3620 且 src=A 而色块仍空=显示层问题。
- **用户实测反馈：绿字有出现（=新 bin、loop/statusBarTask 都活着），但 `[IP5306]` 行超过屏幕调试行宽 36 字符，`adc=` 字段被截断看不到；且用户要求板子上没有 IP5306 芯片、把相关代码注释掉。**
- 据此改动：
  - `shared.h:952-955` V2 分支 `#define BATTERY_USE_IP5306` **注释掉**（不再做 0x75 的 I2C 总线扫描/轮询/四档回退；readBatteryVoltage 走纯 ADC，永不到 IP5306）。
  - `utils.cpp` statusBarTask：删 `batteryOnline` 变量与 IP5306 总线扫描块（否则 -Werror=unused-variable）；`batteryIsCharging=false` 恒定（USB 检测本来就走 IO39/usbPowerPresent，不走 I2C）；长诊断行换成短行 `DBG("[BAT] V=%d src=%c adc=%d usb=%d\n", ...)`（33 字符，行宽内）。
  - ip5306.cpp/h 本身保留（独立编译单元、无调用者，无告警），后续彻底删除再议。
- 注意：batteryIsCharging 恒 false 与此前实际行为一致（芯片离线返回 false），插头图标走 usbPowerPresent 不受影响。
- **真相大白（15:2x）**：用户报屏幕诊断 `[BAT] V=3401 src=A adc=1691` → **读数链路完全正常**（ADC 纯电池下有效，src=A）。VBAT≈3.40V 低于曲线最低点 3450mV→0%（utils.cpp:567）→ lit=0 → 4 格全空框，与"未测到"的空框一模一样 → 被误判为"色块不显示"。**根因：电池耗尽**（早上 3.734V≈20%，测了一整天掉到 3.4V）；"插 USB 才亮"= 充电抬压到 3.9V+ → % 升 → 亮格，拔掉后 peak-hold（~330s 慢衰减）保持高值几分钟 → "拔掉后正常"。
- **教训（重要，防复蹈）**：电量条 0% 与"未测到"不能同渲染。已修：`drawStatusBar` 中 `batteryPercentage>=0 && lit<1 → lit=1`（0% 点亮第 1 格红块，空框只表示未测到）。
- 复盘：今天"冷启动色块不亮"两次发作的完整解释——第一次是真 bug（s_disp 锁 0，已修+用户验证过）；第二次（本节）是电池耗尽的 0% 空框伪装成故障。2s 时序大概率是无辜的（但已回退，未单独复验）。后续若再报"色块不亮"，先看 [BAT] 行 V 值再动手。

## WiFi Deauther / ProbeRequestFlood "发几帧就停"修复（18:5x）
- 症状：去认证/探测请求泛洪，堆 8 万多、成功率 100%，开启后 packet 短暂增加几个就停止；重开循环复现。
- 根因（两处叠加，两个 namespace 是复制代码，问题相同）：
  1. **堆门控阈值 80000 贴脸**（原 wifi.cpp:4807/5495）：攻击期堆基线 ~85k，循环 UI + 80211_tx 每帧内部缓冲分配 → 瞬时跌破 80000 → `attack_running=false` 静默停攻击。屏显 "Heap: 8xxxx" 是 drawAttackScreen 每 2s 的瞬时快照，跌破时刻不可见。
  2. **`static uint32_t last_channel_check = 0` 初值 bug**（原 wifi.cpp:4828/5516）：开机 15s 后启动攻击，`current_time-0>15000` 首拍成立 → 立即 checkApChannel → staWifiScanSync 全信道同步扫描（阻塞 2~4s + 驱动扫描堆开销数 KB）→ 扫完堆跌破 80k → 门控杀攻击。"增加的几个 packet"= 扫描开始前发出的帧。
- 修复（wifi.cpp，两 namespace 各两处）：堆门控 80000→40000（80211_tx 只需几 KB，仍留余量）；`if (last_channel_check == 0) last_channel_check = current_time;` 首拍起算，避免开局立即全信道扫描。
- 排除项：后台自动扫描被 `!feature_active` 门控，攻击期间不跑（wifi.cpp:2035）；checkApChannel 内 WiFi.mode(WIFI_AP)+delay(100) 保留。
- 用户自行编译。若复测仍停：看屏上 Status 是否 Stopped（=门控/失败路径）还是 Running 但 packet 冻结（=循环被阻塞，另查）。
