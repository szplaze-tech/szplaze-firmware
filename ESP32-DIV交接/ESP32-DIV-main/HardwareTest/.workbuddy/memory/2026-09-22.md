## HardwareTest 交互式自检改造（自动带停顿 ⇄ 按键转手动单步）

需求：自检太快看不清 → 每项之间加停顿；自动过程中按键立刻停；之后每按一次键自检一个外设，顺序不变。

实现（单文件，`HardwareTest.ino` 725 → 912 行）：
- 引入**步骤表** `kSteps[]`（`struct TestStep {kind, name, title, fn}`）+ `STEP_COUNT`，
  把原来的 `runAllTests()` 拆成 `beginRun()` / `runStep(i)` / `finishRun()` / `advanceStep()`。
  顺序与原 `runAllTests()` 逐项一致，共 **22 步**（4 条分组标题 + 18 个检测步骤）。
- 粒度调整：`testSystem()` 拆成 `testChip/testFlashPsram/testHeap`；`testNrf24()` 拆成
  `testNrf24Slot(i)` + 三个包装 `testNrf24_1/2/3`（原来一个函数一次画 3 行，拆开才看得清是哪颗挂）。
- 调度器在 `loop()`：三种状态 —— 自动（可中断停顿后 advance）/ 手动（等按键沿才 advance）/ 已跑完（按键重开一轮，模式沿用）。
- `pauseInterruptible(ms)`：停顿期间每 20 ms 轮询按键并在屏幕最底行刷新倒计时，返回 true = 用户按键要求中止自动。
- `STEP_PAUSE_MS = 1500`（步间停顿）、`KEY_POLL_MS = 20`，都在文件顶部可调。
- 按键提前到 `setup()` 里 `keyInit()`（Wire.begin(8,9) + PCF8574 寻址 0x20-0x27），
  否则自动流程跑到一半才初始化按键就"按不动"。

**PCF8574 按键读法的关键结论（读库源码得出）**：
- 库的 `pinMode()` **只改对象内部掩码、不下发 I2C**；`begin()` 仅当该对象 `writeMode|readMode` 非零时
  才 `_wire->write()` 一次。所以只要 begin() 在任何 pinMode() 之前调用，就**全程只读不写**，端口保持上电默认全 1。
- 库的 `digitalRead()` 有**冷启动假象**：首次读会因掩码未初始化返回 LOW（误报"全部按下"）；
  且按对象缓存字节（`latency` 窗口内不重读）。故调度器改用**裸 I2C 直读端口字节**（`keyRawDown()`，
  `beginTransmission` + `endTransmission(false)` + `requestFrom`，~0.2 ms/次），不依赖库的缓存与准双向读逻辑。
- 原文件里的 `anyKeyDown(PCF8574&)` 只被旧 loop() 用过，改造后成了死代码 → 删除（否则 `-Werror=unused-function` 风险）。
- `keyEdge()` 的 armed（先全松开才认下一次按下）在"按下停止自动"与"手动推进"之间共享，
  因此**停止自动的那一次按键不会被当成手动模式的第一步**，必须松手再按才推进。

编译验证（arduino-cli，工程原 FQBN，PSRAM=disabled / min_spiffs）：
- 常规配置：EXIT=0，860169 B flash (43%)，46092 B RAM (14%)。
- `--warnings=all` 严格模式：首次 EXIT=1，命中 `-Werror=format-truncation`
  （`showManualHint()` 的 `char buf[24]` 放 `"key = next  (%d/%d)"` 最坏需 29 字节）→ 缓冲加大到 32 后 EXIT=0。
  该告警正常编译不报，只有严格模式暴露，属真 bug。
- 库内部阻塞（SD.begin 1–3 s、WiFi.scanNetworks 1–2 s）期间收不到按键，按键落在这些窗口要等该项跑完；
  步间停顿 1.5 s 就是为了让绝大多数按键落在可响应窗口内。此限制已写入文件头注释。

## 实机反馈修正：按键无效 + CC1101 自检不对

陈工实机反馈：① 按键按下不停自动流程；② CC1101 自检结果与业务代码不一致（业务代码能操作 CC1101）。

### 根因一：PCF8574 初始化顺序错了（我的实现偏离了业务代码）

业务代码 `ESP32-DIV/utils.cpp:initPcf8574Buttons()` 的顺序是 **先 pinMode ×5，再 begin(addr)**；
PCF8574 库的 `begin()` 只在对象掩码非零时才 `_wire->write(resetInitial)`，其中
`resetInitial = writeModeUp | readMode = 0x00 | 0xF8 = 0xF8`。
**所以业务代码那次 begin() 是真的把 0xF8 写进端口，把 5 个键位主动拉高**。
我上一版推理"pinMode 不下发 I2C，端口保持上电默认全 1，所以只需读不用写"——理论自洽但**未经实机验证**，
只依赖扩展芯片的上电/遗留状态。已改回与业务代码一致：pinMode ×5 → begin()。

另外一个设计缺陷：`keyEdge()` 依赖 `armed`（先全松开才武装）。若端口字节读到全 0（键位为低），
`armed` 永远不为 true → 按键被永久忽略，而且**屏幕上没有任何提示**（静默失效 = 最坏的可观测性）。
已加诊断：底部状态行尾部显示实时端口字节 `k=XX`（V2 空闲应为 0xF8，按键时对应位变 0），
扩展芯片不在时显示 `NO KEY`；串口在字节变化时打 `[key] raw port = 0xXX`。

### 根因二：CC1101 自检缺了业务代码依赖的两步

已核实引脚与 shared.h 完全一致（V2: SCK12/MISO13/MOSI11/CS5），读协议也正确
（`0x30|0x80`=0xB0 读 PARTNUM，SRES 是纯命令 0x30 —— **两者字节值相同，靠读标志位区分**）。
缺的是：

1. **总线回收**：业务代码 `utils.cpp:reclaimSharedSpiBus()` = `SD.end()` → `SPI.end()` → `gpio_reset_pin(数据脚)`
   → `SPI.begin(CC1101_SCK, CC1101_MISO, CC1101_MOSI, CC1101_CS)`。
   工程里有实测注释："**SD.begin raises SPI clock and parks the card on the same MISO line CC1101 needs**"。
   HardwareTest 的顺序恰好是 SD 测试紧接 CC1101，却没有做这步回收。
   已验证**排除**的假设：`SDFS::end()` → `sdcard_uninit()` **不会** `spi_bus_free`（只注销 FatFS），
   所以"总线被 SD 关掉"不成立；nRF24 之所以正常是因为 `RF24::begin(&fspi)` 会自己重新 begin 总线。
2. **SRES 硬复位**：ELECHOUSE `Init()` 开头是 `setSpi(); SpiStart(); digitalWrite(SS,SCK,MOSI...); Reset();`
   而 `Reset()` = CS 低→1ms→高→1ms→低 + `while(digitalRead(MISO))` + `SPI.transfer(0x30)` + 再等就绪。
   我的版本只发了 SIDLE(0x36)，没有 SRES。

已补齐：新增 `ccBusReclaim()` / `ccReset()` / `ccStrobe()` / `ccWaitReady()` / `ccDead()`；
首次读失败会自动补一次 SIDLE+SRES 再读（成功则信息里带 ` 2nd` 标记，说明芯片需要复位才能读）；
串口打印 `[cc1101] SO idle=? after=? try? -> PARTNUM/VERSION`，失败时屏幕信息带 `SO0/SO1`（MISO 是否被别的器件占住）。

顺带核实：`spiAttachMISO()` 里有 `pinMode(miso, INPUT)`（esp32-hal-spi.c:232），
所以读 MISO 做忙等待是安全的，不会反向驱动芯片 —— 这个疑点排除。

### 编译验证

- 原配置：EXIT=0；严格模式 `--warnings=all`：EXIT=0。
- 严格模式又抓到一个真问题：`keySuffix()` 里 `snprintf(dst, n, "k=%02X", g_lastKeyByte)`，
  `%X` 收到 int 最坏输出 8 位十六进制（"output between 5 and 11 bytes into a destination of size 10"）。
  修法：先 `(unsigned)(g_lastKeyByte & 0xFF)` 收窄值域，同时把调用方缓冲 `char ks[10]` → `[16]`。

## 实机关键数据：PCF8574 空闲 0x40（新固件生效，诊断栏奏效）

陈工实测：**空闲 `k=40`，按中间键 → `k=00`**。解读：

- bit6 = SELECT（与 shared.h V2 的 `BTN_SELECT=6` 吻合）在空闲为高、按下变低 → **按键读取链路是通的**；
- **bit7/5/4/3（UP/DOWN/LEFT/RIGHT）恒为 0**，从来没被拉高过 —— 这才是问题本体。

**"按了没停下"的直接原因（现已闭合）**：`keyRawDown()` 只要有"任一键位为低"就返回 true，
而 bit7/5/4/3 恒低 → 函数恒 true → `keyEdge()` 里的 `armed` 永远不为真 → 按键被永久忽略。
所以不是"没读到按键"（SELECT 的电平变化确实被读到了），而是被这个恒真条件吞掉了。

**库的端口写路径被掩码过滤（读源码得出，重要）**：
```cpp
// PCF8574.cpp digitalWrite() / digitalWriteAllBytes() 实际下发的是：
byteBuffered = (writeByteBuffered & writeMode) | (resetInitial & readMode);
_wire->write(byteBuffered);          // ← 不是参数原值
```
`resetInitial = writeModeUp | readMode`（`PCF8574_SOFT_INITIALIZATION` 未定义），且只在
begin() 的 `if (writeMode>0 || readMode>0)` 分支里赋值。所以掩码不对时**写了等于没写**。
空闲 0x40 就说明端口里是个"只有 bit6 为 1"的值，bit7/5/4/3 从未被写过 1。

**已改的实现**：
1. `keyInit()` 改为**裸 I2C 整字节写 0xFF**（`Wire.beginTransmission + Wire.write(0xFF)`），绕开库掩码。
   0xFF = 8 脚全弱拉高（全输入态）；比库的 0xF8 更安全（0xF8 会把 bit0-2 拉低，那是掩码运算副产物）。
   副作用是好的：若按键其实接在别的位，写 0xFF 后按下任何键都能在 `k=` 上看到变化。
   同时删掉了 5 个 `pinMode()` 调用（它们只会让 begin() 走掩码路径）。
2. 写回读后派生 `g_keyGoodMask = idle & KEY_MASK`，**只把空闲确实为高的键位纳入判定** ——
   个别脚被外部拉低时不会拖死整块按键。屏幕 `k=` 末尾带 `!`，串口打 `usableKeys=0x??`。
3. 串口新增 `[key] PCF8574 @0x20 write 0xFF -> idle=0x?? usableKeys=0x??`。

**下一步需陈工回报的判据**：
- 若 `idle=0xF8` → 之前是锁存值不对，已修好，5 键都可用；
- 若仍 `0x40` → **bit7/5/4/3 被外部拉低，属硬件**（疑似串 10k 对地：PCF8574 弱上拉仅 ~100µA，
  10k×100µA≈1V 低于 VIH → 恒读 0；而 SELECT 的接法不同所以正常）。届时量这 4 个脚对地电阻即可确认。
- 若按方向键能看到 `k=` 变化，把变化前后值回报即可反推真实位映射。

## 我的回归：删掉 pinMode 导致"芯片找不到"（PCF8574 库 begin() 的隐藏耦合）

陈工反馈新固件**按下按键毫无变化**。根因是我上一版删掉了 5 个 `pinMode()` 调用：

```cpp
// PCF8574.cpp
bool PCF8574::begin(){
    this->transmissionStatus = 4;          // ← 哨兵值
    ...
    if (writeMode>0 || readMode>0){        // ← 只有进了这个分支才会真正发 I2C
        ...
        this->transmissionStatus = _wire->endTransmission();
    }
    ...
    return this->isLastTransmissionSuccess();   // == (transmissionStatus == 0)
}
```

**掩码为 0 时既不写端口，`transmissionStatus` 也停在 4 → `begin()` 恒返回 false。**
于是 `pcfBeginAny()` 扫完 0x20-0x27 都"失败" → 判定芯片不在 → `g_keyReady=false` →
屏幕显示 `NO KEY`（不变化的文字）→ 表现为"按键毫无反应"。**库把"探测成功"和"刚才有没有写端口"绑死了。**

**同一个坑还害了原有的 `testPcf8574()`**：它也在任何 `pinMode` 之前调 `pcfBeginAny`，
所以这一项**一直误报 `FAIL not found`**（芯片其实在）。属原工程遗留 bug。

### 这一轮的修法

1. **地址探测改为标准 I2C 探测** `pcfProbe()`：`beginTransmission(a); endTransmission()==0` 即命中
   （与 `testI2cScan()` 同一手法），彻底不依赖库的 `begin()` 返回值。
2. **端口读写全部走裸 I2C**：`pcfReadPort(addr)` / `Wire.write(0xFF)`。删掉 `g_keys` 对象、
   `pcfBeginAny()`，以及 `#include <PCF8574.h>` —— 本自检不再用那个库（注释里写明了原因）。
   `testPcf8574()` 也改成裸读，报 `0x20 11111` 形式的逐键电平，结论与屏幕 `k=` 栏、与按键实际行为三者一致。
3. `keyInit()` 现在记录 **写前 before / 写后 after** 两个读数（区分"锁存值不对"与"引脚被外部拉低"），
   并把"写后多读 4 次取或"来算 `usableKeys` —— 之前只看单次读就算掩码，一次坏读就会把整块按键判死。
4. **底部状态行改为始终刷新**（新增 `statusTick()`）：跑完整轮停在结果页时那行原本不再更新，
   导致"按键没反应"和"屏幕没刷新"看起来一样、无法区分。现在任何状态都实时显示按键字节，
   并每 5 s 打一行串口心跳（`[key] live ... (loop alive)`）顺带证明没卡死。

### 教训（同类库的通用陷阱）

判断"外设探测是否成功"时，**不要用带状态耦合的库 API 当探测器**（尤其是返回值依赖"之前做过什么"的）。
用最原始的物理层探测（I2C 地址 ACK / SPI 读 ID 寄存器）最可靠。这与本工程 CC1101 直接读
PARTNUM/VERSION 而不是调 `Init()` 的判断，是同一条经验的两次印证。

## 卡死在 [HSPI 35/36/37] LCD + TOUCH —— 原工程遗留的总线争用 bug

按键修好后陈工反馈：跑到 LCD/TOUCH 这一组屏幕卡住。**这不是本轮改动引入的**，是原版
`testTouch()` 就有的问题，只是被"步间停顿"暴露出来了（之前表现为"太快看不清"，实际是复位循环）。

三个事实拼起来就是根因：

| 事实 | 位置 |
|---|---|
| TFT_eSPI 在 S3 上自建 `SPIClass spi = SPIClass(HSPI);` | `Processors/TFT_eSPI_ESP32_S3.c:15` |
| 并在 IDF 层 `spi_bus_initialize(HSPI_HOST/SPI3_HOST, ...)` + `spi_bus_add_device` | 同文件 `:874-876` |
| Arduino 的 `spiStartBus()` 在 S3 分支**无条件 `periph_module_reset(PERIPH_SPI3_MODULE)`**，且**没有任何"已被占用"检查**（`spi_t` 是 Arduino 自己的静态数组，TFT_eSPI 走 IDF 不经它） | `cores/esp32/esp32-hal-spi.c:735` |
| 原版 `testTouch()` 却 new 了第二个 `SPIClass hspi(HSPI)` 并 `hspi.begin(36,37,35,18)` | 原 HardwareTest |

→ 那句 `hspi.begin()` **把 TFT 正在用的 SPI3 外设整个复位**，TFT_eSPI 的设备/DMA 句柄随即失效；
下一次 `tft.print`（即 XPT2046 那一行的绘制）就是死等 → 屏停在 LCD/TOUCH 这一组。

### 修法（对齐业务代码 V2 已验证路径）

业务代码 `Touchscreen.cpp` 在 `TOUCH_SHARES_TFT_SPI`（V2）分支里 **只 `pinMode(XPT2046_CS, OUTPUT)`
+ 置高，不建 SPI 实例**，读触摸走 TFT_eSPI 内建 API。据此：

- 删除全局 `SPIClass hspi(HSPI)` 与 `xptRead()`；
- `testTouch()` 改为 `tft.getTouchRaw(&x,&y)` + `tft.getTouchRawZ()`；
- TFT_eSPI 的 `init()` 本来就会 `pinMode(TOUCH_CS, OUTPUT)`（`TFT_eSPI.cpp:543`）✓
- `getTouchRaw()` **无压力门限、无条件读原始 X/Y 且恒返回 true**，正好当在位判据；
  X/Y 未触摸时也有值（几百~几千），只有全 0 / 全 4095 才是 SPI 上没器件。
- 格式化前掩 12 位（`(unsigned)(x & 0x0FFF)`），避免 `%u` 收到 int 时的格式截断告警。

### 通用教训

**同一外设在 ESP32 上只能有一个"总线所有者"**：TFT_eSPI 这类库会绕过 Arduino 的 SPIClass
自己 `spi_bus_initialize`，而 Arduino 的 `spiStartBus()` 不查占用、直接复位外设。
凡是要访问挂在屏幕同一条 SPI 上的器件（触摸/XPT2046），一律走 TFT_eSPI 暴露的 API，
不要自建第二个 `SPIClass`。

## LCD/TOUCH 这一步"卡 7–8 秒"的构成与节流

陈工澄清：不是死住，是**卡七八秒后继续**，并要求别在这一步长时间阻塞。时间构成（估算）：

- 该组共 1 个分组标题 + 2 个设备步骤 = **4 次 1.5 s 停顿 ≈ 6 s**；
- 加上 `tft.readcommand8()` 的读开销 —— TFT_eSPI 每调一次都要把整条 HSPI
  从写模式切到读模式再切回（`begin_tft_read/end_tft_read`：重配 MISO + 频率切到
  `SPI_READ_FREQUENCY` = 20 MHz），原版连读 3 次就来回切 3 遍。

已做的节流与实测手段：

1. **分组标题行画完不再停顿**：`nextPauseMs()` 在 `g_lastKind == STEP_GROUP` 时返回 0 —
   标题只是小标题，和组内第一项一起看即可。HSPI/I2C 组各省一拍，FSPI 组省更多。
2. **LCD ID 由读 3 次改为读 1 次**（`report("LCD ID   CS17", ..., "%02X", d1)`），
   判据仍是"非 0x00 / 非 0xFF = MISO(GPIO37) 回读线通"。
3. **每步耗时实测并显示**：`advanceStep()` 用 millis 包住 `runStep()`，结果
   ① 串口打 `[step 11/22] LcdId   12 ms`、② 屏幕最底行在停顿期间显示
   `LcdId 12ms  next 1.4s  k=F8`（`statusLine` 定宽加宽到 34 字符以容纳）。
   这样"哪一步慢、慢多少、是硬件等待还是固定停顿"一眼可分，不再靠猜。

**这一步的用途与判据**（回答陈工的问题）：
- `testDisplayId`：读 ILI9341 的 RDDIDIF(0x04)，验**回读通道**（MISO=GPIO37，屏唯一要回读的线）
  与控制器型号；屏在不在其实屏幕自己能证明（这些行就是它画的），这一步专门覆盖"能显示但读不回 ID"的情况。
- `testTouch`：读 XPT2046 原始 X/Y（12 位电阻分压，**未触摸也有值**，典型几百~几千）与 Z（压力）。
  全 0 / 全 4095（MISO 恒定不动）才判 FAIL；按住屏幕 Z 会明显抬升，可人手复核。

**待陈工回报**：改完后 LcdId / Touch 两行各自显示多少 ms —— 如果 LcdId 仍是几百上千毫秒，
说明瓶颈确实在 TFT 的读模式切换，届时可以考虑彻底不读 ID（屏的显示本身就是充分的在位证据）。

## 白屏事故（我引入的回归）—— 屏读命令是唯一"业务固件没做过"的操作

陈工反馈烧了上一版后**直接白屏**。定位依据（决定性）：

```
业务固件（本板已验证可用）用到的 TFT 操作只有两处：
  ESP32-DIV/Touchscreen.cpp:48  tft.getTouchRawZ()
  ESP32-DIV/Touchscreen.cpp:57  tft.getTouchRaw(&rawX, &rawY)
  —— 全库 grep 无任何 readcommand / readPixel
```

而 `testDisplayId()` 用的 `tft.readcommand8()` 是**整个自检里唯一业务固件从未做过的屏操作**。
它的危害在 S3 上是实打实的：
`Processors/TFT_eSPI_ESP32_S3.h:122-126` 里
`SET_BUS_READ_MODE = *_spi_user = SPI_USR_MOSI | SPI_USR_MISO | SPI_DOUTDIN`
—— 置了 `SPI_DOUTDIN`（MOSI 变双向），整条 HSPI 被切成读模式。
白屏 = 背光还亮着但面板没有内容（面板未初始化/被复位）。还发现 `Extensions/Touch.cpp` 的
`end_touch_read_write()` 里那句 `SET_BUS_WRITE_MODE` 是**被注释掉的**，靠下一次
`begin_tft_write()` 补（`TFT_eSPI.cpp:74`，且仅当内部 `locked` 为真时才补）。

### 修复

1. **`testDisplayId()` 默认不再读屏**：新增编译开关 `#define ENABLE_LCD_ID_READ 0`，
   关闭时该行报 `N/A  skip: display=proof` —— 屏在不在屏幕自己能证明（那些测试行就是它画的）。
   需要排查「能显示但 MISO(GPIO37) 回读线不通」时把开关置 1 复测。
2. **`testTouch()` 改为逐行照搬业务代码顺序**：`tft.endWrite()` → `getTouchRawZ()` → `getTouchRaw()`，
   并在读完后补一次 `tft.drawPixel(0,0,TFT_BLACK)` 强制把总线切回写模式（对上述被注释掉的
   `SET_BUS_WRITE_MODE` 做一层保险，代价一个像素）。
3. **`beginRun()` 开头加 `tft.init()` + `setRotation(2)` 自愈**：万一某轮把屏留成白屏/半初始化状态，
   按键重开一轮即可恢复画面，不必重新烧录（第二次 `tft.init()` 安全：TFT_eSPI 内部 SPIClass
   的 `_spi` 已非空，不会再 `periph_module_reset` HSPI）。

### 教训（重要，反复踩到同一个模式）

**"业务固件没做过"的硬件操作 = 高风险区。** 自检固件相对业务固件是"新代码路径"，
凡是超出已验证路径的操作（屏读命令、第二个 SPIClass、库的掩码写端口）都应当：

屏读命令）全部踩在这条线上。

## 按陈工要求定稿：触摸改人工校准式检测 + 行历史重画

陈工的三条要求：
1. 显示屏不用做额外检测（程序一跑就能看到屏在不在）；
2. 这条总线（HSPI）上的检测：显示屏只读 ID 就够，然后是触摸 IC；
3. **触摸检测用"触摸校准"的方式，必须有文字提示、必须测试人员点击，点完才继续下一步。**

### 落地的实现

- **`testDisplayId()` 保持默认不读屏**（`ENABLE_LCD_ID_READ 0`），该行报
  `N/A  skip: display=proof`。理由已在上一节说明（屏读会把 HSPI 切成读模式 → 白屏）。
  陈工要恢复 ID 回读的话把该宏置 1（届时建议同时加"读完立刻 tft.init() + logReplay()"的恢复）。
- **`testTouch()` 重写为人工交互的 4 角靶标检测**：
  - 整屏画文字提示（`TOUCH TEST` / `Press & hold each target until it turns green.` /
    `4 targets, 15 s each.` / `Any key = skip this test`）+ 4 个角十字靶标（22/-23 边距内缩）；
  - 每点 `waitTouchDown(15000)` → 命中变绿 → `waitTouchUp(3000)`；4 点完成或某点超时才退出；
  - **每一点都有超时**，绝不用 TFT_eSPI 的 `getTouch()/calibrateTouch()` ——
    它们内部的 `validTouch()` 有 `while (z1 > z2)` 无界等待，触摸 IC 一坏就永久挂死自检；
  - 压力阈值 `TOUCH_Z_MIN = 300`（业务代码用的是 120 / 200 / 500，取中间值）；
  - 读取用非阻塞的 `getTouchRawZ() + getTouchRaw()`，顺序照搬业务代码（先 `endWrite()`），
    读后补 `drawPixel(0,0,TFT_BLACK)` 强制切回写模式；

    给操作者一个逃出 4×15 s 等待的口子；
  - 结果：4/4 → OK；1~3 → FAIL "n/4 pts"；0 → FAIL "no touch"；原始 X/Y 范围与耗时打串口。
- **新增"行历史 + 重画"机制**（`g_logLabel/Info/St/Color` + `logPush/logClear/logReplay/drawFrame`）：
  交互页会整屏覆盖，重画后已完成的测试行不会丢，后续步骤继续往下堆。

### 1. 新增 USB/充电插入检测（IO39 分压电路）

> V2: 原为 GPIO5 —— 与 CC1101_CS 同脚。GPS 模块只要上电就持续输出 NMEA，
> **该网络物理上常连通，模块 TX 会不停在 CC1101 片选线上制造跳变**，造成随机片选 / 误写寄存器。

## CC1101 检测不到的真凶：状态寄存器要用 burst 位读（0xC0，不是 0x80）

陈工提示"我在业务代码里是操作模块的"，据此去搜业务代码/库的读取方式，找到了确凿差异：

```cpp
// ELECHOUSE_CC1101_SRC_DRV.cpp
bool ELECHOUSE_CC1101::getCC1101(void){          // 库自带的"模块在位"检测
  setSpi();
  if (SpiReadStatus(0x31) > 0) return 1;          // 读 VERSION
  return 0;
}

byte ELECHOUSE_CC1101::SpiReadStatus(byte addr) {
  SpiStart();
  temp = addr | READ_BURST;                       // ← 0xC0（读位 0x80 + burst 0x40）
  digitalWrite(SS_PIN, LOW);
  while(digitalRead(MISO_PIN));                   // ⚠ 无界等待！
  SPI.transfer(temp);  value = SPI.transfer(0);
  digitalWrite(SS_PIN, HIGH);
  SpiEnd();
  return value;
}
```

**PARTNUM(0x30) / VERSION(0x31) 属于状态寄存器，必须用 burst 位访问（header = addr | 0xC0）。
我此前一直用 addr | 0x80（单读），读不到东西 —— 这就是"CC1101 检测不到"的根因。**

### 改法

- `ccReadReg()` → `ccReadStatusReg()`：header 改成 `addr | 0xC0`，注释写明原因与库出处。
- **新增方法 A：直接走库的在位检测**（`setSpiPin + setGDO + getCC1101() + SpiReadStatus`），
  即业务固件那条已验证路径 → 成功时行内标 `lib`。
- 方法 B：裸读 burst 形式（`0xC0|addr`）→ 标 `raw`；方法 C：先 `ccReset()` 再裸读 → 标 `raw2`。
- **重要安全门禁**：库的 `SpiReadStatus/Reset` 里有 `while(digitalRead(MISO));` **无界等待**，
  芯片不在时会永久挂死自检 —— 所以先用**有超时**的 `ccStrobe(0x36)`+`g_ccSoReady` 确认
  SO 能变低，**只有 soReady 为真才允许调库**。
- `ccLibRead()` 内部在读完调一次 `ccBusReclaim()`：库的 `SpiEnd()` 会把 SPI 四脚设成 INPUT，
  不重新接管的话后续自己的 `fspi` 传输会失效。
- 失败签名不变：`CS5 busy(N)!` / `SO stuck hi` / `XX XX`；成功信息带方法名（`lib`/`raw`/`raw2`）。
