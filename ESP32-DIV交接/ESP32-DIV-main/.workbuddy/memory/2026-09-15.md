## 红外发射脚迁移：GPIO14 → GPIO46（用户硬件改造）

### 起因

V2 的 `IR_TX_PIN=14` 与 nRF24 #3 的 `CE_PIN_3=14` **共用一个脚**（作者原注释已警告）。
红外发射时 IRsend 把该脚当输出翻转 ⇒ **拉低 nRF24 #3 的 CE** ⇒ 干扰 2.4G 功能。

### 改动（仅一行宏）

`shared.h` V2(else) 分支：`IR_TX_PIN` **14 → 46**。
`IR_TX_PIN` 全部引用都走宏（`ir.cpp:62 kSendPin`、`ir.cpp:1411 / 1996 IRsend`），无硬编码，改一处即全生效。
⇒ 改后 **GPIO14 归 nRF24 #3 的 CE 独占**。

编译：**EXIT=0，零告警**，Sketch 1766025 B (89%)（宏值变化不改代码体积）。

### ⚠ GPIO46 的硬约束（ESP32-S3 strapping 脚）—— 必须遵守

GPIO46 是 S3 四个 strapping 脚之一（GPIO0/3/45/46），**默认弱下拉**，兼 **ROM 启动日志开关**。

1. **硬件严禁在该脚加外部上拉**：尤其 `VCC → LED → 限流电阻 → GPIO` 的**灌电流接法**，
   会把上电瞬间的 GPIO46 拉成 1 → **ROM 启动日志被禁用**（`ESP-ROM:esp32s3-...` 那几行消失），
   且与 `GPIO0=0`(按 BOOT 键) 组成**无效组合**，可能进不了下载模式。
2. **必须用低侧驱动**：`GPIO46 → 限流电阻 → 三极管基极 / LED → GND`。
3. 软件侧安全 ✅：IRsend 只在进入红外功能时 `pinMode(kSendPin, OUTPUT)`（`ir.cpp:1194`），
   上电期间该脚高阻/内部弱下拉 → 复位采样值为 0。
4. **自检法**：烧录后看串口首行是否仍有 `ESP-ROM:esp32s3-20210327 / mode:DIO, clock div:1` ——
   若消失，说明 GPIO46 被外部上拉了。

### 仍存在的共用（未处理，待用户决定）

`IR_RX_PIN=21` 仍与 `CSN_PIN_3=21` 共用。红外接收用 GPIO21 的 CHANGE 中断采样（退出功能时已调
`IRRemoteFeature::s_recv.disableIRIn()` 清理中断），但两者物理同脚，无法同时使用。
若日后还要纯 2.4G 使用，接收侧是下一个隐患点。

## 红外接收脚迁移：GPIO21 → GPIO40（同日 14:55）

### 起因

`IR_RX_PIN=21` 与 nRF24 #3 的 `CSN_PIN_3=21` 同脚：红外接收在 GPIO21 挂 CHANGE 中断，
而该脚同时是 SPI 片选 ⇒ 两个功能无法共存。

### 改动

1. `shared.h` V2(else) 分支：`IR_RX_PIN` **21 → 40**；
2. 更新 `shared.h` 的 IR 说明块（原写"默认与 NRF24 #3 重叠"，V2 已解耦）；
3. `ir.cpp` 三处退出清理注释同步更新（原注释还写着"GPIO21 同时是 CSN"）——
   用 `replace_all` 一次改 3 处，已核验：旧文案 0 残留、新文案 3 处。

选 GPIO40 的理由：工程零占用（`shared.h` 里无任何引脚宏定义它）、**非 strapping 脚**（无外部
上拉限制，这点比 46 好）、是 S3 的 JTAG **MTDO** —— eFuse 默认时 JTAG 走内置 USB Serial/JTAG，
不占 GPIO39-42，仅外部 JTAG 调试器接入时才被征用。

编译：**EXIT=0，零告警**，Sketch 1766025 B (89%)。

## ESP32-DIV 2.4G「干扰功能」的实际发射频率（17:20）—— 为配合用户的 nRF24 测试环境

### 用户目的（已澄清）

搭了 STM32 + nRF24 **收发对**（TX 发自增数字 / RX 接收，2440 MHz = ch40、1 Mbps、地址 0xE7×5、0 dBm），
用来**客观验证 ESP32-DIV 的 2.4G 干扰功能**（BLE Jammer / ProtoKill）是否真的把干扰发出去。

### 查代码结论（两个功能逻辑完全相同，`bluetooth.cpp:3225` / `5118`）

```cpp
void configureRadio(RF24 &radio, const byte* channels, size_t size) {
  ... setPALevel(RF24_PA_MAX,true); setDataRate(RF24_2MBPS); setCRCLength(RF24_CRC_DISABLED);
  for (size_t i = 0; i < size; i++) { radio.setChannel(channels[i]); radio.startConstCarrier(RF24_PA_MAX, channels[i]); }
}
initializeRadiosMultiMode(): radio1→channelGroup1{2,5,8,11}  radio2→{26,29,32,35}  radio3→{80,83,86,89}
```

**RF24 库 `startConstCarrier()` 内部每次都会 `setChannel(channel)`**（已读 RF24.cpp 确认）⇒
for 循环连续调用 4 次后，**每颗模块只停在「组内最后一个信道」** —— 定义了 12 个信道，**实际只发 3 个单频点**：

| 模块 | 信道组 | **实际发射点** |
|---|---|---|
| radio1 | {2,5,8,11} | **2411 MHz (ch11)** |
| radio2 | {26,29,32,35} | **2435 MHz (ch35)** |
| radio3 | {80,83,86,89} | **2489 MHz (ch89)** |

发射参数：`RF24_PA_MAX` + LNA、2 Mbps、CRC disabled、AutoAck off，`CONT_WAVE|PLL_LOCK` ⇒ **持续常量载波**（setup 时调一次，一直发）。

### 对本次测试的影响（关键）

用户 RX 在 **2440 MHz (ch40)**，离最近的实际发射点 2435 差 **5 MHz**；
nRF24 常量载波有效带宽仅 ~1–2 MHz ⇒ **干扰不到，会误判成"干扰功能失效"**。

**建议**：把 STM32 两端 `NRF24_CHANNEL` 40 → **35（2435 MHz）**，即命中 radio2。
（备选：11 / 89，或改 ESP32-DIV 的信道组以覆盖 2440 —— 但 2440 落在 WiFi ch6 频带内，不推荐。）

### 附加诊断价值

若干扰生效 ⇒ 反证 **ESP32-DIV 板载 nRF24 的 SPI 发射链路是通的**（至少 #2），
可直接续上 2026-09-10 暂停的「板载 nRF24 无反应」排查。
测前记得整机重启（清 IR 引脚残留），三颗模块天线都要插。

## 修复 2.4G 干扰功能的「信道覆盖」bug（17:30）

用户要求：修掉「本意覆盖 12 个信道，实际只有 3 个点在工作」。查代码后发现是**两层问题叠加**。

### 问题 1：`configureRadio()` 的 for 循环白跑 3 次

BleJammer / ProtoKill 各有一份（文本完全相同）：
```cpp
for (size_t i = 0; i < size; i++) { radio.setChannel(channels[i]); radio.startConstCarrier(RF24_PA_MAX, channels[i]); }
```
RF24 库 `startConstCarrier()` **内部每次都会 `setChannel()`**（已读 `RF24.cpp` 确认）
⇒ 循环跑完**只停在组内最后一个信道**（2411 / 2435 / 2489 MHz），前 3 次纯属白跑。

### 问题 2（更严重）：loop 里三颗「同步」跳同一个信道

`blejamLoop()` / `protoKillLoop()` 里：
```cpp
int ch = <信道表>[random(0, n)];
radio1.setChannel(ch); radio2.setChannel(ch); radio3.setChannel(ch);   // ← 三颗同一个信道
```
⇒ **任一时刻只覆盖 1 个频点**，另外两颗完全白跑；`channelGroup1/2/3` 的「三颗各盯一组」设计
被彻底覆盖、从未生效。且每 loop 迭代（`delay(1)`）就跳一次，信道停留 <1ms（< PLL 锁定 ~130us），效率低。

### 修复（5 处编辑 + 1 处前向声明）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `configureRadio()` ×2（`replace_all`） | 删掉 for 循环，只在 `channels[0]` 建立载波；`(void)size;` 保留参数 |
| 2 | BleJammer（插在 `blejamSetup()` 前） | 新增 `bleJammerHop()`：BLE 模式用 **channelGroup1/2/3 索引同步推进**（`(idx+1)&0x03`）⇒ 任一时刻覆盖 3 个不同频点、**一轮 4 跳扫过全部 12 个信道**；其他模式取 3 个互不相同的信道（`base / base+n/3 / base+2·n/3`）。节流 `kBleJamHopMs = 4` |
| 3 | `blejamLoop()` | 那段 if/else → `bleJammerHop()` |
| 4 | ProtoKill（插在它的 `exit()` 前） | 新增 `protoKillHop()` + `protoHopSpread()`，用 `switch` 覆盖全部 **8 个模式**（BLE/Bluetooth/WiFi/USB_Wireless/VideoTX/RC/Zigbee/nRF24）；BLE 同样三组轮换。节流 `kProtoHopMs = 4` |
| 5 | `protoKillLoop()` | 58 行的 8 分支 if/else → `protoKillHop()` |

**踩坑**：`protoKillHop()` 插在 loop **之后** ⇒ 编译报 `'protoKillHop' was not declared in this scope`。
加前向声明解决：ProtoKill 的 `bool jammerActive = false;` 之后加 `void protoKillHop();`
（BleJammer 的 hop 插在 loop 之前，无此问题）。

### 修复后的干扰行为

- **BLE 模式**：三颗各盯一组 → 任一时刻覆盖 3 个频点（如 2402/2426/2480），
  每 4ms 组内各推进一格 → **16ms 扫完全部 12 个信道**（2402–2411 / 2426–2435 / 2480–2489）。
- **其他模式**：三颗错开取信道表里的不同点，同时覆盖 3 个频点（原来只 1 个）。
- 用户那套 nRF24 测试环境（RX 在 2440 MHz = ch40）**仍不在覆盖范围内**：
  最近的实际发射点是 ch35 = 2435 MHz。测试时把 STM32 两端改到 **ch35 / ch11 / ch89** 任一即可命中。

### 补充：修复后各模式的「实际覆盖强度」不同（由分配算法决定）

`protoHopSpread(arr, n)` 用 `step = n/3`，三颗取 `arr[base] / arr[(base+step)%n] / arr[(base+2·step)%n]`
⇒ **当 n == 3 时三颗【一对一】，表内信道 100% 被覆盖**；n > 3 时只覆盖 3 个点。

| 模式 | 信道表 | 三颗分配 | 每信道占空比 |
|---|---|---|---|
| **USB Wireless** | {40,50,60} = **2440/2450/2460** | 一对一 | **100%** ⭐ |
| **Video TX** | {70,75,80} = 2470/2475/2480 | 一对一 | **100%** ⭐ |
| **nRF24** | {76,78,79} = 2476/2478/2479 | 一对一 | **100%** ⭐ |
| RC | {1,3,5,7} = 2401~2407 | 覆盖 3/4 | ~75% |
| Zigbee | {11,15,20,25} | 覆盖 3/4 | ~75% |
| BLE | 12 个（3 组轮转） | 各盯一组 | 25% |
| WiFi | {1..12} | 错开 3 点（step=4） | 25% |
| Bluetooth | 21 个 | 错开 3 点（step=7） | 14% |

**对用户测试的意义（重要）**：他的 RX 在 **2440 MHz = ch40**，正是 **USB Wireless 模式**信道表的第一个
⇒ **选 USB 模式可直接命中，STM32 端一个参数都不用改**（先前建议改 ch35 是针对 BLE 模式的）。
预期现象：OLED 自增数字**停止更新**（持续载波把 -85 dBm 的有效帧完全淹没），关干扰立即恢复；
因为是**纯载波无调制数据**，nRF24 收到的是 CRC 失败帧 → 硬件丢弃 ⇒ **不会出现乱码值**。

## 干扰实测结果（17:46）：干扰有效，但打不动 nRF24 链路，只影响 WiFi

用户实测：ProtoKill → **USB 模式**（信道 {40,50,60} = 2440/2450/2460）开启干扰后，
**STM32 的 nRF24 链路照常收到自增数字**（预期的"OLED 数字停住"未发生），
但**明确观察到 2.4G WiFi 被干扰**。

### 判读

1. **干扰确实在发射** ✓ —— WiFi **ch6 = 2437 MHz（占 2427–2447）正好覆盖 2440**，被压制是直接证据；
   同时也**反证 ESP32-DIV 板载 nRF24 的发射链路是通的**（至少负责 2440 那颗）。
2. **nRF24 没被打下来 = 信干比问题（距离/功率），不是功能 bug**：
   - 板上是**普通 nRF24L01（非 +、非 PA 版）⇒ 最大发射功率只有 0 dBm（1 mW）**；
     干扰源功率**完全相同（0 dBm）** ⇒ 干扰与信号功率对等，胜负**完全由距离决定**。
   - FSPL(dB) = 20·log10(d_m) + 20·log10(f_Hz) − 147.55（f = 2.44 GHz）：
     TX–RX 距 **0.1 m** ⇒ 信号 ≈ **−20 dBm**；干扰源距 RX **1 m** ⇒ 干扰 ≈ **−40 dBm**
     ⇒ **信干比 +20 dB，RX 照样能解包**。
3. WiFi 之所以"看起来更受影响"：WiFi 设备（路由/网卡）通常离干扰源更近，且窄带强载波会直接抬升其底噪。

### 修正后的测试方法（关键在距离）

- 把 **ESP32-DIV 的 2.4G 天线贴到 RX 天线上（1–3 cm）**，同时把 TX 拉远到 **1–2 m**；
- 或把 TX 功率降到最低（RF24 `PA_MIN` ≈ −18 dBm）人为压低信号；
- 或在 TX↔RX 之间串衰减器。
- 验收标准：**信干比转为负值**（干扰强于信号）后，OLED 自增数字应立即停更。

### 可选增强（待用户决定）

`protoHopSpread` 目前每 4 ms 重新随机 base ⇒ 每颗模块每 4 ms 都要重设信道
（PLL ~130us 重锁 + 短暂空档）。若要"最狠的连续压制"，可改为**锁定不再重排**
（三颗固定停在一个分配上）或加长 hop 间隔，消除切换空档、做真正 100% 连续载波。
