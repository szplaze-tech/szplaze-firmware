## 中文界面改造可行性评估（10:05）

用户问：界面能否中英文切换。

### 现状调研

| 项 | 实测 |
|---|---|
| 字体 | 全工程用 **TFT_eSPI 内置字体**（`setTextFont(1)`/`setTextSize(1)`），**无任何自定义字体文件**（无 vlw / lv_font / 中文点阵）→ **内置字体纯 ASCII，不含中文字形** |

### 技术路线（三个必要件）

1. **中文字库**：统计界面用到的**去重汉字**（估 400~800 字）→ 生成 16×16 点阵 C 数组；

2. **中文绘制函数**：`drawZhText(x,y,str,color)`，逐字查表 + 画点（或 `pushImage`）；
3. **字符串表**：把 UI 字面量收敛成表；**真正的成本在这里**——496 处 `tft.print` + 33 个菜单数组。

### 两种切换方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 编译期宏**（`#define UI_LANG_ZH`） | 只存一套字符串、改动小、省 Flash | 换语言要重新烧录 |
| **B. 运行时切换**（双字符串表 + `g_lang`） | 可随时切 | **字符串表翻倍占 Flash**；每个 print 都要改成查表调用，改动最大 |

现在 font1 约 **6×8 px**；中文最小 12×12 或 16×16 → 一个汉字≈2.7 个英文字符宽。
- 240×320 屏上很多行只够 15~20 个英文字符；中文长词条（如 "MouseJack Inject"→"鼠标注入"）需**逐个微调布局**，这是隐性大头。

### 建议

**分阶段**：阶段 1 只做**菜单文字**（33 个数组集中、改动可控）验证字库+布局；阶段 2 再扩 496 处功能内文字。**推荐编译期宏切换**（嵌入式惯例，省 Flash）。

**待用户定**：①范围（仅菜单 / 全部文字）；②切换方式（重烧 vs 运行时）；③能否接受中文 12~16px 带来的布局调整。

## 阶段 2 实施（10:40 ~ 11:00）

**用户反馈三条**：①中文背景色要与菜单背景一致；②子菜单进入后大部仍是英文；③一二级菜单用 16×16，功能内部文字用 12×12 且**全部翻译**。

### 关键根因：pushImage 的字节序问题（解释①）

读 TFT_eSPI 源码发现 `pushImage(x,y,w,h,data,transp)` 的透明实现：

```cpp
if (!_swapBytes) transp = transp >> 8 | transp << 8;   // transp 被字节交换
uint16_t color = pgm_read_word(ptr);                   // 与原始 buffer 比较
if (transp != color) { ... }
```

默认 `_swapBytes == false` 时，**传入的 transparent 被字节交换后与未交换的 buffer 比较 → 永不相等 → 透明失效、退化成全部绘制**。而且 pushImage 走的是与 `drawChar` **不同的写入路径**，颜色会出现字节序偏差——深色主题下背景近黑（0x0000）看不出来，稍有色调的底色（如 `UI.bg` 深蓝灰）就会显示成**偏色的方块** → 这就是用户看到的"背景色不一致"。

**修复**：汉字改为**只画前景点**（`tft.drawPixel` / `fillRect`），不填背景 → 任何底色上都正确，也彻底绕开字节序问题。包在 `startWrite/endWrite` 里减少事务开销。

### 三点要求的实现

| 要求 | 实现 |
|---|---|
| ① 背景一致 | `drawGlyph()` 只绘制为 1 的位，不再填充背景色 |
| ② 菜单用 16×16 | 按**当前字高自动选字号**：`useGlyph16(fh) = fh >= 16`（菜单用 `setTextFont(2)`=16px → 16×16） |
| ③ 功能内 12×12 + 全量翻译 | 功能内多为 `setTextFont(1)`=8px → 12×12；翻译表扩到 **296 条**，并把 **1804 处文字调用**批量换成 ui 镜像 API |

### 经验（可复用）

- **TFT_eSPI 小图块绘制优先用 drawPixel/逐行 setWindow，别用 pushImage**：pushImage 的字节序/透明语义依赖运行时 `_swapBytes`，行为不可预期。

```cpp
template <typename T> inline void uiPrint(const T& v)   { tft.print(v); }   // IPAddress/Printable/其它
template <typename T> inline void uiPrintln(const T& v) { tft.println(v); }
inline void uiPrint(double v, int dp)                   { tft.print(v, dp); }
```
（非模板重载在同等匹配下优先于模板，所以 `const char*` / `String` / 整型仍走会翻译的版本。）

另外发现并处理的两类调用：`uiPrintln(uint16_t)`（数字 println——原先只声明了 const char*/String，靠模板兜底解决）、`uiPrint(float, int)`（小数位形式）。

## 字形质量修正（11:54，用户反馈 12×12/16×16 中文"有点扭曲"）

## 导航栏未汉化修正（14:42 用户反馈"子菜单最下方导航栏没有完全汉化"）

### 两个根因

1. **标签从未进翻译表（主因）**：导航栏文字是**函数参数字面量**——
   `setTouchNavLabels("Exit", "Delete", "Run", ...)`、`FeatureUI::drawButtonRect(...,"Back",...)`、
   `footerToast("No changes")`、`drawPanelFrame(...,"Progress")`、`showFeatureUnavailable(...,"This feature requires ESP32-S3.")`。
   首版抽取器只扫 `tft.print/drawString` 的**字面量**，所以这 78 个标签一个都没被收录 → `T()` 匹配不到 → 保持英文。
   **修法**：写 `extract_labels.py`，按"函数调用实参中的字符串字面量"抽取（含配对括号解析 + 顶层逗号切分），
   得到 78 个标签；补进翻译表后复查**未翻译 0 个**。
   另补：`pagedPageBtnLabel()` 里 `return "Next Page"/"Prev Page"`（return 出来的字面量，另一种漏网形式）；
   IR 遥控器按键/设备类型（`PWR/MUTE/VOL±/CH±/UP/DOWN/LEFT/RIGHT/BACK/TV/AVR/AC/STB/GAME/FIT/PROJECTOR`，已核对**只出现在 ir.cpp，无跨用途冲突**）；
   `OPEN`（WiFi/GPS 认证方式 → 开放）、`Unknown`（→ 未知）。

2. **`fitTouchNavLabel()` 双重缺陷**：
   ```cpp
   String out = label;
   while (out.length() > 1 && uiTextWidth(out + "...") > maxWidth) out.remove(out.length() - 1);
   ```
   - **先截断英文、再翻译** → 截过的标签永远匹配不到翻译表（长标签必现英文）；
   - **按字节 `remove(len-1)`** → 中文 3 字节/字，会截出**半个汉字**（非法 UTF-8）显示成乱码。

## 汉字残影 / 遮字 / 乱码三连（16:32）

用户报三个现象：①重放攻击「协议：0 xxx」xxx 是乱码；②SubGHz 干扰里「模」被黑块遮住一部分；③状态文字切换后有上一字的残影。

### 统一根因（一条主线 + 两处布局碰撞）

**主线：12px 汉字在 8px 的 font1 行里是"上下各溢出 2px"绘制的（见 `i18n.cpp` 的 `zhDy() = (字高-12)/2` → font1 得 -2），所以字形实际占 `y-2 ~ y+10`。而所有"先 fillRect 清行、再写字"的清屏矩形都是 `fillRect(x, y, w, h)`（从 y 起、h≈11~13）→ 顶部 2 行永远清不到 ⇒ 上一字的顶部笔画残留 = 用户看到的"乱码/残影"。**

- **① 乱码**：重放屏 ptc 值单元格 `(170, w=40)` → 清屏 `170..210`，与模式值单元格 `(175, w=40)` → `175..215` **互相重叠**；且绘制顺序是 mode 先、ptc 后 ⇒ ptc 的清屏把模式的中文（自动/手动/锁定）从 y 起切掉 11 行，**只留 y-2、y-1 两行**，于是"0"旁边多出一排残笔画 = 乱码。
- **② 遮字**：干扰屏频率值单元格 `(40, w=96)` → 清屏 `40..136`，而「模式：」标签从 **130** 起（中文 3 字 = 36px，英文 "Mode:" 只 30px）⇒ **「模」左侧 6 列被抹掉**。这个碰撞在英文下也存在（"Mode:" 也从 130 起），只是英文笔画稀疏不明显——中文把它放大了。
- **③ 残影**：即主线本身。

### 修法（三层）

1. **让汉字自己清干净自己的格子**（`i18n.cpp drawGlyph`）：画点之前先 `fillRect(x, y, w*sc, h*sc, s_bg)`（`s_bg == s_fg` 表示透明背景，此时不清）。这样原地更新的文字不会留上一个字的笔画。
2. **清屏矩形统一上移加高**：新增全局宏 **`UI_CJK_TOP_PAD 3`**（`i18n.h`，= 2px 溢出 + 1px 余量）。共修 **9 处**：`replayDrawValueCell` / `jammerDrawValueCell` / `jdDrawValueCell`（subghz）+ `subghz.cpp` 的 4 处 `kLineH-1` 列 + `ir.cpp:395` + `rfid.cpp:807`。
   ⚠ 踩坑：第一版把常量 `kCjkCellTopPad` 定义在 replay 所在**命名空间内**，jammer/jd 命名空间看不见 → 编译报 `not declared in this scope`；改用 i18n.h 的全局宏后解决。
3. **消除横向碰撞**：重放屏 ptc 格 `w 40→20`（170..190）、模式格 `x 175→192`；干扰屏频率格 `w 96→86`（40..126）、模式格 `x 165→168`。

- 图示 `.workbuddy/i18n/mock_cell_geometry.png`（垂直清屏范围 / 水平越界 两张示意）。

### 通用规律（重要）

**任何"清行再写字"的矩形，高度必须 ≥ 汉字高度(12) 且上边要上移 2px**；**任何按英文标签宽度算出的值列 x，翻译成中文后都要重算**（中文 1 字 = 12px ≈ 2 个 ASCII 字符）。这两条是本项目汉化中最容易反复踩的坑。

## 上传在 55% 掉线（17:23）

错误：`A serial exception error occurred: Cannot configure port ... PermissionError(13, '设备不识别')`，固件写到 **55%** 中断（写之前都正常，说明链路本身通）。

### 实测证据（本机设备树 + 系统日志）

- 失败后 **COM11**（`USB\VID_303A&PID_1001&MI_00\7&383C4049&0&0000`，S3 原生 USB CDC）**Present=False** —— 设备从总线消失；
- 当前 present 的 USB 串口只剩 **COM15**（`...\7&264ADDFA&0&0000`）⇒ **换了电脑上的 USB 插口实例**（CDC 的 COM 号按 USB 端口实例分配，换口即换号）；
- 系统日志 17:17~17:23 共 11 条 `hcmon: Detected unrecognized USB driver (\Driver\hrdevmon)`（VMware USB 仲裁 × 火绒 hrdevmon 老冲突，本身无害），**频率侧面反映该窗口 USB 设备多次接入/移除**。

### 根因判断

**用 ESP32-S3 原生 USB-CDC 烧写 1.76MB 大固件**是已知脆弱组合：flash 擦写期间长时间禁用 cache/中断 → USB CDC 掉线 → esptool 句柄失效 → PermissionError 13。本板有 IP5306 供电塌坑史，写入期大电流会加剧。次级因素：换插口后 COM 号漂移、IDE 仍选旧端口；若经过 USB hub 会恶化。

### 处置（按序，最省事优先）

1. IDE → 工具 → **Upload Speed 921600 → 115200**，重传；
2. 确认 **USB 直连电脑主板口（不要经过 hub）**，端口选**当前实际存在的那个**（现为 COM15）；
3. 仍失败 → **改用板载 USB-UART 外部桥（CP2102 / CH340 口）烧写**：外部桥不受 flash 操作影响，是大固件最稳的通道；
4. 兜底：esptool 命令行 + `--baud 115200`。

**要点**：这是烧写期问题，与固件内容无关；烧成功后运行不受影响。

## "设置无法保存"排查（18:15）

用户报：现在无法保存设置参数，重新烧录也一样。

### 机制（已查证，非本轮 i18n 改动引入的回归）

- 设置存 **SD 卡 `/config/settings.json`**（`SettingsStore.h:8`），**不是内部 flash / NVS**；
- 保存链路（`utils.cpp:2252-2271`）：触摸 Save → `dirtySettings ? settingsSave() : toast("No changes")`；
  `settingsSave()` 依次做 `ensureDir("/config")` → `SD.open(..., FILE_WRITE)` → `serializeJson(doc,f) > 0`，
  **任一步失败即返回 false → 屏显 "Save FAILED"（保存失败）**；
- 排除回归：我加的 `lang` 字段只让 `StaticJsonDocument<512>` 多占约 20 B（实测总用量约 340 B，远未溢出）；
  `SettingsStore.h (struct 正常) / .cpp (读写逻辑未被改动)`。

### 两个关键隐蔽点

1. `updateSdCardStatus()`（utils.cpp:601）只读 **SD_CD 引脚（GPIO38）**——屏上/串口出现 "SD Card detected"
   **仅代表卡物理插着，不代表文件系统可用**；
2. SD 与 **CC1101 / nRF24×3 / PN532 共用同一条 SPI**，代码注释已明说：
   `// FatFS "exists(/)" can stay true after another feature stole the SPI bus. cardType() actually talks to the card`
   ⇒ **进过 Scanner / ESB / RFID / SubGHz 等功能后，SPI 被重绑，SD 可能挂不上**（`isSDCardAvailable()` 会 `SD.end()` 后软重挂）。

### 判据（按 Save 时屏幕提示）

| 提示 | 含义 |
|---|---|
| **保存失败**（Save FAILED） | `settingsSave()` 返回 false → SD 介质/挂载问题 |
| **无更改**（No changes） | `dirtySettings=false`，本次没改动任何项 |
| **已保存**但重启无效 | 写入成功、读取失败（少见） |

### 建议改造

设置改存 **ESP32 内部 NVS（Preferences）**，彻底不依赖 SD 卡：手持设备拔卡是常态、FAT 在掉电时易损坏，
而本板掉电史严重（IP5306 塌坑）。NVS 只需几十字节、掉电安全。可保留 SD 作为可选备份/导出。
